# 内部一致性审查：派遣参考

本页供主代理组装子代理任务书。每个 worker 收到“共同任务书 ＋ 专属角度说明 ＋（可选）最小实例取证块”。

## 一、共同任务书骨架

```text
你是本轮内部一致性审查的收集者，负责〈角度编号与名称〉。
只读审查：零修改仓库文件、零触碰生产服务与共享队列。

被审体系与目标：〈体系简述；本次审查要抓出的行动冲突〉。
有效依据：〈已确认的设计裁决与现行规范；当实现与已确认裁决冲突时，以已确认裁决为准报告实现偏差〉。
材料清单：〈该角度必读文件/目录列表；允许顺调用链与 refer 追查关联文件〉。

请站在实际使用点逐处核对：谁在什么条件下拿到什么信息、执行哪个命令或写入什么产物、下一步由哪个门禁或下游怎样消费。重点捕捉六类问题：
1. 怎么提交交代模糊，或提示词要求格式与门禁实际接收格式不同，或外部/上游实际给到的变量与文档承诺的不同；
2. 前面说了后面推翻；
3. 多条规则或机制同时触发时互相卡死；
4. refer 指向的目标缺失，或跳过去之后没有当前动作需要的那条信息；
5. 流程中首次出现并影响行动的概念缺少可操作解释；
6. 同一概念换用多个词，或同一词在上下游指代不同对象。

本轮为自由探索：无需顾虑与其他角度重复，撞上同一问题照报。

每条发现必须写齐五项（缺一不可）：
1. 位置与原话（精确到文件:行号 + 原文摘录）；
2. 具体适用情境（哪个角色、在哪个状态、满足什么前提时走到这里）；
3. 比较的另一端及证据（另一处原文摘录，或门禁/脚本的具体函数与行号）；
4. 冲突如何成立（两边合在一起怎样导致行动失败、卡死或写出非法产物；若属歧义，写出两种合理读法各自导出的不同动作）；
5. 最小修复方向。

所有候选按三类分栏交付：
- 已证实冲突：两端原文或代码路径已完整闭合，行动冲突必然发生；
- 待补证候选：已抓到冲突线索，写出还差哪份运行材料或外部条件即可拍板；
- 表达可改善：规则本身可执行，改写后能省去读者的具体猜测步骤。

报告末尾附“覆盖账”：列出已逐项核对完的关系、状态边、命令分支，以及未查到的剩余范围。
将完整报告写入〈权威输出路径〉，首行标『〈角度编号〉』。
```

## 二、关系轴专项块（菜单乙 W1–W8）

### W1：规范文本语义与跨状态责任

```text
通读〈提示词、手册、跨状态规范〉，逐条对齐同一规定的执行主体、触发条件、生效时点和约束强度。
必核：
1. 单个状态内部的多条要求能否同时满足，有无前文允许、后文封死的自相矛盾；
2. 跨状态交接时，前态承诺产出的条件与后态假定已成立的前提是否严丝合缝；
3. 同一概念在不同文档中换词或同词异义时，写出两种读法各自导出的具体动作差异；
4. 每条 refer 跳转到目标章节后，是否真有当前动作急需的格式、字段或命令说明；
5. 流程中首次出现的专有概念，在执行者此刻可见的材料里能否拿到明确做法。
交付成对原文摘录、冲突情境推演，以及“责任×状态×角色”核对表。
```

### W2：指令、CLI 接口与权限白名单

```text
逐条追踪〈提示词与手册中出现的全部命令、工具调用、参数模板〉到〈脚本 argparse/入口解析、权限白名单配置、返回值构造〉，建立三方对照表：指令原文 × 实际调用形状 × 接口与权限。
必核：
1. 工具、子命令、脚本路径、位置参数与选项名、必填/可选、默认值、枚举域及路径基准是否完全一致；
2. 状态机的工具权限白名单与 bash 细分规则是否放行指令要求的每一条命令（区分模型直接调用与门禁内部执行）；
3. 接口的四类返回（成功、拒绝、无变化 no-op、半途部分失败）在文档中有无对应的后续动作说明，是否存在接口返回某种状态而执行者按文档不知道怎么接的缺口。
```

### W3：状态转移、硬门副作用与软审材料（高密度主轴）

```text
枚举〈全部 FSM YAML〉的每一个 state 与每一条 transition，按真实执行序逐边走读：入态条件 → 执行者动作 → 出态硬门校验 → 硬门写盘副作用 → 软审（LLM 评审）读取的材料与判据 → 状态提交 / 拒绝留态后的重试出路。
必核：
1. 指令要求执行者先完成的动作，与出态硬门实际检查的库表、文件、git 状态是否一致；是否存在按指令做完仍被未交代的隐藏条件拦住的情况；
2. 硬门包含写文件、覆盖报告或改库副作用时：①是否提前覆写或销毁了紧随其后的软审要求核对的原始材料；②一旦软审拒绝、流程留在原状态等待重试，硬门刚才写下的文件是否会触发该状态的写保护或完整性检查，把所有重试出路彻底封死；
3. 正常推进、失败回退、人工分流、异常恢复四类出边的触发条件是否互斥且覆盖完整，被拒后执行者手头的权限白名单是否允许它完成要求的修复动作。
交付全量转移边核对矩阵；每条高危死结附完整代码执行路径或最小探针结果。
```

### W4：父子派遣与上下文展开

```text
沿“父状态指令 → 派遣注册调用 → 引擎/脚本模板展开 → 子代理首轮收到的真实上下文与任务包 → 子状态指令 → 提交与父侧回收”追踪整条派遣链。
必核：
1. 每种任务类型（常规批次、专项分析、复核等）在注册时写入的字段、阶段标识、目标执行器名称，与子代理消费时读取的字段名、路径、身份标识是否逐字对齐；
2. 模板展开后注入给子代理的变量名、任务包 JSON 字段、预置底稿路径，同子代理提示词里宣称“外部会给到你 XX”的描述是否完全一致；
3. 子代理按规定提交的完成标志与产物，是否正好满足父代理轮询、结算和进入下一态的判定条件。
输出逐任务类型的四段交接对照表。
```

### W5：产物生成—接收—合并—下游消费全链

```text
锁定体系内的核心数据工件〈函数稿、共同稿、发现记录、回执、图数据库/导出 JSON、汇总报告〉，逐个追踪从落笔到最终消费的完整生命周期。
必核：
1. 生产者被要求写的章节标题层级、必填字段、枚举值、空集合/不适用写法，与接收门禁的正则/schema 校验器是否严丝合缝；
2. 接收与合并逻辑对预置模板、新增条目、既有底稿的保留/覆盖/丢弃规则，是否与提示词向执行者承诺的生命周期一致；
3. 上游阶段写入的字段或标记，在下游阶段是否有真实的读取者；下游阶段依赖的输入字段，上游门禁是否真有强制校验保证其存在。
交付每个核心产物的“生产要求 × 门禁校验 × 合并落盘 × 下游读取”四方链路表。
```

### W6：多机制共享状态与顺序交互（高密度主轴）

```text
找出多个机制共同读写或共同依赖的状态对象〈任务队列、节点状态、版本号、输入快照、在途批次、锁与工作树〉，按事件交错顺序推演组合冲突。
必核：
1. 发现上报/类型变更 × 原任务继续交付：任务中途改变节点性质或挂起新请求时，当前批次的提交门禁还能否通过；
2. 范围裁剪/图变更/全局重审 × 在途批次与已接受成果：上游改动共享状态后，在途批次如何结算、已接受节点如何判定失效、固定不可变节点是否会被连带强制要求重交；
3. 版本身份追踪：失效判定依赖的“输入版本”取的是真实已接受输入代次，还是会被正常的多步提交冲掉的相邻 git commit；
4. 暂停调度 × 死批恢复 × 跨宿主环境（如不同运行器有无守护进程地址）：恢复命令与状态查询在各目标环境下能否走通，半途注册失败会留下什么无法清理的残余状态。
每条发现写出完整事件序列（T1→T2→T3）、共享状态变化与卡死点。
```

### W7：已确认要求与跨工件版本承接

```text
从〈负责人已批准的裁决记录、设计文档、提示词骨架〉提取全部有效要求，逐条追踪其在现行提示词、手册、门禁脚本及安装/生成快照中的落地状态。
必核：
1. 已明确拍板的裁决是否已完整写入对应提示词与门禁，有无“文档改了、门禁没改”或“门禁拦了、提示词没教”的半截工程；
2. 仓库内存在源码模板、生成产物或主副镜像（如 `skills/` 与发布副本）时，各副本之间是否存在代差；
3. 历史遗留说明或旧版命令残留是否仍在现行手册中误导执行者。
交付“有效要求 × 提示词 × 门禁代码 × 镜像副本”承接对账表。
```

### W8：测试覆盖账与反假绿（高密度主轴）

```text
审查〈测试目录与测试 runner 脚本〉，核对测试体系能否真实守住上述状态机与门禁合同。
必核：
1. 覆盖账：列出状态机每条转移边、门禁每个核心拒绝分支分别由哪个测试函数验证，标出零测试覆盖的裸奔分支；
2. 假绿路径推演（重点）：
   - 测试 runner / 汇总器是否在子测试失败、导入报错或全量 skip 时仍返回退出码 0 或记为 passed；
   - 续跑/缓存机制是否把上一次的旧绿结果直接当成当前通过；
   - 测试 fixture / helper 是否在底层静默补齐、改写或吞掉了生产 CLI 必传的参数与标志（导致生产调用会崩、测试却永绿）；
   - 专项测试是否把恰好处在被测核心路径上的校验函数给 mock 掉了，或者只断言终态文件存在、未断言真正走过目标分支；
3. 对比基线被删除或搬移的测试文件，核查它们原本守护的契约现在由谁承接。
每条假绿发现必须给出“当被测代码坏成什么样时，该测试依然绿灯通过”的静态执行路径。
```

## 三、消费者镜头专项块（菜单甲）

```text
你将扮演首次接手〈角色名（如阶段 worker / 主调度者）〉的执行者，手头只有该角色在运行时合法可见的提示词、手册与任务包字段，不携带任何隐含背景。
请按真实工作流从头走到尾：接单 → 读输入 → 调工具分析 → 写产物 → 跑自检 → 提交过门禁 → 处理异常或拒绝。
在每一步追问：
1. 光看当前可见文本，我知道具体敲哪条命令、传什么参数、写哪个文件、填什么格式吗？
2. 有哪一步必须靠猜，且猜 A 和猜 B 都会显得合理、却会导致其中一种被门禁打回？
3. 遇到异常、重入或门禁报错时，手册给出的下一步动作在我当前的权限白名单下能执行吗？
按执行时间线交付全部卡点与歧义点。
```

## 四、十分钟最小实例取证块（按需拼入 W2/W3/W4/W5/W6）

```text
实例取证许可：你可在 `/tmp` 自有临时目录下，调用仓库现成测试 fixture 或 CLI 初始化最小测试库，跑通 1–2 条真实命令链，直接抓取真实的任务包 JSON、命令回执和门禁报错文本，与提示词原文逐字比对。
边界：零触碰生产服务与当前工作区文件；单个实例若 10 分钟内无法搭通，立即停止搭环境，退回静态代码推演并在报告中注明。
```

## 五、主代理回收、打捞与修复派发

### 1. 超时与长耗时处理

- **超时打捞**：发现 worker 超时，先读取其 session transcript 末尾的 `write` 工具调用参数，提取已生成的报告正文落盘；确属未完成再补派。
- **长耗时收尾导航（steer）**：
  ```text
  收尾指令（主代理）：完成当前正在运行的这一条命令后立即停止扩展实验。将已完成核对的结论按三类分栏写入报告，需要额外运行环境才能确认的条目列入“待补证候选”并写明所缺条件，写盘后立即结束。
  ```

### 2. 裁定后修复 worker 任务书骨架

```text
修复执行（〈责任域名称〉）。
工作树：〈独立 git worktree 路径〉（分支 〈分支名〉，基于 〈基线 commit〉）。
先读：〈DECISIONS.md〉（已附负责人拍板结论）、〈NON-DECISIONS.md〉及〈对应原始审计报告路径〉。
修改范围：严格限于 〈该域允许修改的文件/目录列表〉；零 git commit/stash/checkout 操作，改完保留在工作树交主代理验收。

修复清单：
〈逐条列出：编号 → 目标文件 → 具体行为变更与验收标准〉

执行要求：
1. 严格按拍板结论与最小修复方向落代码/改文案，保持周围无关逻辑不动；
2. 逐项单跑对应的定向测试文件确认通过，为新增分支补齐直接走过该分支的回归用例（拒绝用只查终态或 mock 掉被测函数的假测试充数）；
3. 交付修复对照表（编号 → 修改文件:行号 → 新行为说明 → 实跑测试命令与退出码）及 `git diff --stat`。
```
