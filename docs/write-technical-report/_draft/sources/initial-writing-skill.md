# 对外技术文档写作

让读者知道：要解决什么，方案能做什么，怎样生效，依据是什么，还有哪些限制。写清楚，不以字数最少为目标。

## 写作步骤

### 1. 确认用途与材料

- 确认读者要据此判断什么，以及本次允许改哪些内容。
- 阅读用户指定的样文。学习它怎样交代对象、条件、结果和依据，不照搬项目术语、数字或结论。样文也可能有修辞、错误和过期内容。
- 保留用户的目标和验收要求。改写目标的表达，不降低目标，也不因写作而增加功能。
- 材料不足时指出缺少什么。不把设计写成实测结果，不把猜测写成事实。

本技能的风格样本见 参考记录（本地参考，未随归档提供）。它们不是每次写作都必须重读的依赖；当前用户提供的样文优先。

### 2. 逐句检查形容词和状语

问：这个词在当前句子里说明了哪个对象、动作、条件、范围、数量或结果？

- **没有提供信息**：删除。称赞、强调、营造气势和替结论表态的修辞都不保留。
- **信息藏在修饰词里**：从材料中找出它指的行为或要求，改写成明确句子。可以写长，不让读者猜。
- **限定会改变判断**：保留，或用等义句展开。例如“只读”“执行前”“同一次”“所有适用要求”“可能”不能因词性而删除。
- **含义无法确定**：不用自己的设计补空白。若影响结论，指出需要确认的判据；不把含糊评价写成已经达到的能力。

不要使用词语黑名单。同一个词可能是修辞，也可能是条件、数量、时间或代码标识符。删除后检查主张是否变强、变弱或改变了对象。

### 3. 用行为说明方案

- 写谁对什么做什么；有分支时写清触发条件和结果。不要求每句话填满所有要素。
- 用功能代替评价：不只说“灵活”，说明用户可以配置什么；不只说“高强度”，说明检查什么、使用什么材料、何时拒绝。
- 不用“其余情况”“进一步处理”等词省掉会影响行为的条件。条件不同，分句写或列表说明。
- 保留行业术语、代码名和必要的数学概念，首次出现时说明它在本文的用途。不为显得技术化增加缩写和分类。
- 同一对象使用同一个名称。不要将方案意图、配置值、检查结果和运行效果混写。

### 4. 组织正文

- 开头写用途与验收要求，再说明方案，随后用案例展示输入、规则和结果。
- 案例按理解所需的顺序展开。保留词元、参数、路径、条件和失败分支，不为减少篇幅省掉判断所需的信息。
- 用标题标明问题，用表格对照条件和结果。案例末收束判断，文末说明结论、依据和限制；不重复展开。
- 不复述内部争论、方法论分类或改稿过程，除非文档本身要解释这些过程。
- 方案说明使用方案语气，不反复以“尚未实现”开场。涉及覆盖、效果、保证或性能时，必须说明证据范围；目标不是成绩，案例不是测量。

### 5. 核对并交付

- 对照原稿检查目标、功能、因果、条件、范围、数量、否定和证据状态是否保留。
- 检查命令、图、表、变量与正文是否一致；检查引用是否仍支撑对应主张。
- 再读一遍：还有没有只起修辞作用的词？有没有一句话需要读者猜主语、条件或结果？若有，继续改。
- 若删除一个词会丢信息，撤回删除或补成明确句子。不用篇幅下降或词频下降代替核验。
- 交付改后的文档和必要的变更说明，不交付整套写作方法。

## 改写示例

以下示例使用 Tool Auth Lang 已给定的业务规则。换项目时，使用该项目的规则，不照搬这些判断条件。

| 原写法 | 改写 |
|---|---|
| 更自然、更灵活地处理权限 | 用户复用工具规则，在命令、参数或文件节点上增加自己的限制。 |
| 对脚本进行高强度审核 | 审查者读取脚本，检查是否修改禁写文件、向外发送凭证或执行与任务无关的操作。 |
| 其余情况统一审查 | 任一规则拒绝时，不启动 AI Review。没有拒绝但还有待审要求时，将这些要求交给一次 AI Review。 |
| Writable 文件允许操作 | Writable 表示这项写检查通过；整次调用还须满足其他规则。 |

“可能触发”不能改成“必然触发”，“只读工具”不能改成“工具”，“同一次调用”不能改成“调用”。这些限定规定了结论，不是修辞。
