# 快速传递 idea 的技术报告：QPDI 记录

## Task Overview

**问题对象**：以 指定读者 为重点读者时，怎样写一份能快速传递 idea 的 technical report。

**用户确认的目标**：

> 以 指定读者 为重点照顾和目标对象的情况下，一个**快速传递 idea 的 technical report 应该怎么写**的问题。

**当前工作解释**：这里的“快速”指读者较少猜测对象身份、补全前提或重组关键关系，能按阅读顺序把局部理解接回 idea 的整体。它不指作者写得更快、字数更少，也没有已设的阅读时长指标。必要的事实、限制和证据不能为了快而删除。

**本次范围**：固定这项写作方法的 Q 与候选 D。方法应能迁移到不同 idea 及其沟通任务，但本轮不把所有技术体裁的完整写法纳入问题，也不继续设计 Tool Auth Lang。

**不在范围内**：不要求未来报告展示 QPDI 字段；不重开写作理论调研；不修改或替换已安装的 `write-technical-report`；不以说服 指定读者 接受 idea 代替如实、充分地说明 idea。

**主要材料**：用户对 `idea-report.md`、7月9日报告、开头与修饰语的连续校正；[范围校准原文](RECENT-REQUESTS.md)；既有[综合研究](SYNTHESIS.md)；[V08](sources/V08-L2738-edit.md) 与 [V09](sources/V09-L2775-unlogged_change_observed.md) 开头；前轮的[技能候选](SKILL-DRAFT.md)。

**当前状态**：Q.I.1–Q.I.3记录用户已明确的目标与要求；本轮对适用域的解释、Q.A/Q.E的整理及D.root设计仍可校正。候选P、M、R不因落盘而获得确认；已有技能正文是待对账的I候选，尚未安装。

**导航**：[用户目标与前提](#q) → [候选D.root及组件](#d-root) → [既有稿件与同步义务](#sync)

## 状态与引用规则

| 状态 | 本文中的含义 |
|---|---|
| `confirmed` | 内容的规范含义或采纳已由用户明确；仅授权写文件不算内容确认。 |
| `candidate` | 根据已确认材料作出的整理、设计或推导；不因写入文件自动变成用户确认的规范。 |
| `文本已核` | 本地文件中可复查的文字、版本差异或用户评论。它不等于真实读者效果已经测得。 |
| `未测` | 没有真实 指定读者 试读、A/B 对照或技能独立增益证据。 |
| `written` | 本文件已写入；它与内容确认、事实验证分开。 |

## Q — 问题意识

### Q.I.1 — 以 指定读者 为重点，快速传递 idea

**采纳状态**：`confirmed`

**定义**：评价本问题的写法时，以它是否帮助指定读者等重点读者快速形成对本次idea的必要理解为准。在多种满足实际说明任务的写法中，默认优先采用指定读者偏好的表达。

**判断力**：如果一篇稿只给出术语、局部机制或修辞，而读者仍须先猜“这是什么”“它在解决什么”“这些细节怎样共同构成 idea”，它没有满足本目标。反之，不能因追求快而省掉使 idea 不被误解的必要限定、事实或证据状态。

**来源原文**：当前目标见消息`c10d41d5`；偏好取舍见此前消息`406062ab`：“当存在多种候选方案，优先更多倾向 指定读者的审美方案”。两条原文见[用户来源摘录](sources/user-request-excerpts.md)。

**适用边界**：指定读者是重点读者，不是唯一可能读者。本文据此研究传达方法，不承诺对方必然赞同，也没有获得“所有读者都同样快”的保证。

### Q.I.2 — 必要信息与联系不能为“快”让位

**采纳状态**：`confirmed`

**定义**：压缩后仍须正确、充分地说明本次idea需要传达的内容。不能用删掉必要解释、条件或依据来换取篇幅短，再让读者补做本应由作者完成的说明。

**来源**：[范围校准原文](RECENT-REQUESTS.md)中，用户明确要求本段内容表达完全、清晰，并认可“信息充分是裁剪的前提”；同时要求局部理解贡献于整体理解。这是用户的规范要求，不是仅由样文观察推出的经验。

### Q.I.3 — 方法应可迁移，也应能实际采用

**采纳状态**：`confirmed`，指用户此前明确的通用性与可用性要求。

**定义**：结果不能只是对眼前稿件的改词清单；应提供可用于新idea的判断方法，也保留足够具体的做法以供使用。不能以追求一般性为由删空推荐与实例，也不能仅以列举代替对未列情况的判断。

**来源原文**：[消息`406062ab`](sources/user-request-excerpts.md)：“但是我们依然是谋求 General Purpose 的 SKILL”；“我们真的就要一个大概成型的方案以应用的”。

**本轮范围解释**：在Q.I.1指定的快速idea沟通目标下落实这种通用性，不把它缩成两个样文的经验集，也不因此要求本轮交付所有技术体裁的完整写法。这个范围解释不否定较广研究材料的用途。

### Q.A.1 — 用户提供的指定读者读者画像

**采纳状态**：`candidate`，指本条对已有描述的合并整理。

**事实状态**：来源是用户描述，不是独立读者实验。可确认用户作出了这些评价，不据此声称我们已测得其偏好或效果。

**命题**：据用户描述，指定读者偏好明确的对象定位、直接的关系说明、核心办法配贯通案例；他不喜欢需要读者自行解释的修饰词堆砌。[相关描述](RECENT-REQUESTS.md)与[消息`406062ab`](sources/user-request-excerpts.md)支持采用这一工作画像。

**适用范围**：画像不说明指定读者对每个新idea已经知道什么。某一稿件的共享背景仍须从具体委托与材料取得；这些前提由D.1使用。

**重审条件**：若后续反馈不支持该画像，D.2需调整默认表达；这不改变Q.I.1中以指定读者为重点的目标。

### Q.A.2 — 共享词义不等于共享新的说明关系

**采纳状态**：`candidate`

**事实状态**：由用户对 Tool Auth Lang 开头的校正和既有写作材料支持；未测量其对所有读者的效果。

**命题**：读者可能认识 `tag`、`type`、输入或输出等词，但仍不知道这些对象在当前idea中承担什么角色、彼此怎样联系。相反，有些关系已由前文或共同知识建立。因此，词语是否熟悉不足以单独判定该处关系是否已被理解。

**被谁使用**：D.1分辨已有认识与待说明内容；D.2在实际缺口处建立联系，而非给所有熟词重新下定义。这些操作属于D，不作为新的事实命题。

### Q.E.1 — Tool Auth Lang 开头暴露了“手段先行”的定位问题

**采纳状态**：`candidate`

**事实状态**：`文本已核`；关于理解效果的推断为 `未测`。

**观察**：V08 先说明“用类型和标签审核工具调用”；V09 改为先定位“工具调用审核规则描述语言”。用户指出，前者让读者先遇到手段，却不知道 Tool Auth Lang 是什么对象、tag 在其中处于什么位置；后者至少先建立了对象归属。V09中的“下一代”并不因修辞本身构成定位。[V08](sources/V08-L2738-edit.md) [V09](sources/V09-L2775-unlogged_change_observed.md)

**经验结论**：在本例中，手段信息没有代替对象定位；用户指出了这一缺口，并补入类别说明。它支持把对象定位作为D.2的候选做法，不证明所有报告都必须以“X是一种Y”开头。

**被谁使用**：D.2 的开头选择与对象定位。

### Q.E.2 — 7月9日报告展示了信息关系如何决定后文证据的含义

**采纳状态**：`candidate`

**事实状态**：`文本已核`；不是对阅读速度的实验。

**观察**：7月9日报告先将对象说明为程序行为建模引擎，再交代代码项目输入、逐函数行为输出、工程用途、证据口径和限制。由此，后文的覆盖、抽查和缺陷线索可以被区分为不同问题下的材料，而不是单一“系统好不好”的成绩。

**经验结论**：该样文通过对象、用途和评价口径联系后续材料，提供了一种组织实例；它没有证明所有对象都适用输入输出结构。D.2据此选择组织时，仍需有本稿说明任务的依据。

**证据**：[综合研究](SYNTHESIS.md)§5.2记录这一组织观察，§7.2给出原报告路径；只取表达关系，不把原项目数据当成本方法的效果测量。

**被谁使用**：D.2的内容组织与D.3的整体验证。

## D.root — 构造快速传递 idea 的技术报告

**采纳状态**：`candidate`

### Upstream

- `Q.I.1`：以指定读者为重点，快速传递idea。
- `Q.I.2`：必要信息与联系不能为压缩让位。
- `Q.I.3`：方法可迁移且能实际采用。
- `Q.A.1–Q.A.2`：指定读者工作画像、词义与新关系的区别。
- `Q.E.1–Q.E.2`：开头改写与7月9日报告的组织样本。

### P — 本层必须满足的性质

#### P.1 — 忠实并保留当前判断所需的边界

报告不得把设计目标写成实测结果，把局部例子写成全面证明，或为简洁删掉会改变 idea 含义、结论范围、条件或证据状态的信息。

#### P.2 — 读者能接到 idea 的整体

报告在读者需要时交代：它在介绍什么对象或主张、为什么或在何种情境下值得讨论、核心 idea 怎样工作或怎样被判断、以及理解当前结论所需的关键关系。细节必须能接回已经建立的对象与问题，而不是离体出现。

#### P.3 — 信息充分后才减少负担

每项保留内容要完成当前说明，或为后续可追踪的说明提供前提；同时，全部由本次任务触发的必要对象、关系、条件、依据和限制必须已被交代。应删去不承担这些作用的修辞与重复，但不把作者应完成的解释转交给读者。

#### P.4 — 写法可由当前任务实际选择

方法必须说明怎样从委托、纠正、材料和读者处境得到本次必须传递的内容，怎样处理事实缺口与多个合格表达候选，怎样组织和回查。它不能只列“清楚、充分、简洁”等评价词，也不能把固定章序、固定段数或固定测试设为普遍前提。

#### P.5 — 指定读者偏好以条件默认进入实际选择

在不与 P.1–P.4 冲突时，默认优先采用直接的对象定位、关键关系说明、核心办法和贯通案例；保留当前判断所需的依据与边界。读者已知问题时压缩无作用背景；读者尚未共享问题或 WHY 时，先补必要情境。该规则不要求每份 idea 报告附同一套验收表、性能数据或实现手册。

**用户已明确的措辞约束**：原则上不保留状语；禁止连续堆砌形容词/状语。无必要信息的删，有必要含义的写成明确短句。保留必要信息不等于保留修饰形式；少数精度必需的限定不能反过来取消默认。这不是尚待选用的风格提示，已按本次补充授权恢复到候选§5，由D.2落实、D.3核对。

### M — Operational Model

D.root 由三个 component D 组成。它们可以往返：写案例或核对正文时发现缺口，应回到上游 component 改写，不将这三项误作不可逆流水线。

| Component | 父层分配的 contract | 结果去向 |
|---|---|---|
| `D.1` 恢复本次沟通任务 | 从真实材料得到本稿必须支持的理解或判断，并显出会影响内容的缺口 | 为 `D.2` 分配说明义务；为 `D.3` 提供回查基准 |
| `D.2` 构造说明结构 | 把说明义务落实为对象定位、关系、案例、依据与可读表达 | 形成报告草案，交给 `D.3` 整体回查 |
| `D.3` 对账并回改整篇报告 | 检查覆盖、贡献、忠实性和读者负担，并将发现送回相应 owner | 形成当前可交付报告或明确未闭合缺口 |

#### D.1 — 恢复本次沟通任务

**Upstream obligation**：实现 P.1、P.2、P.4 中“本次”而非“现有草稿”决定内容的部分。

**P**：D.1 必须从明确委托、后续纠正、交付用途、当前事实/证据材料和可靠读者已知中，形成可用于取舍的说明任务。例如：读者读完后要能判断或理解哪些具体事情；哪些对象、关系、条件和依据是其前提。不得从已有标题或目录反推任务，也不得把每个读者的私人目的都写成义务。

**M**：

1. 区分当前委托、已接受纠正、可核事实、读者前提和现有草稿；说明它们各自限定什么。
2. 将“读者需要能够理解或判断什么”具体到能发现遗漏的程度。
3. 为每项任务找出所需对象、关系、条件、证据和可能的贯通例子。
4. 分流缺口：事实、目标、授权或证据缺失且影响本次说明时，回到权威材料或提出最小澄清；事实和任务已足够而只是存在多个组织/表达候选时，由作者比较、选择或组合。

**R**：这里承接父层P.4的任务来源要求：D.2使用的是委托与材料所支持的说明义务，而不是从现稿目录倒推的任务。不同来源分别规定用途、可作主张与解释深度，不组成可相互抵消的优先序。无需把内部判断另存成任务矩阵或读者画像。

**候选 implemented-by**：[SKILL-DRAFT §1](SKILL-DRAFT.md#1-先取得本次报告要完成的事情)、[§2](SKILL-DRAFT.md#2-由任务构成必须说明的内容)。它们是已有I候选的对账位置，不表示已确认满足本次作用域或已安装。

#### D.2 — 构造说明结构

**Upstream obligation**：将D.1得到的说明义务组织成报告，保持P.1的忠实性，并满足P.2、P.3、P.5分配的整体联系、内容取舍与条件化默认要求。

**P**：D.2 必须让读者在需要时获得对象定位、核心 idea、关键关系、条件、依据和边界；开头、正文、图表、案例和句子共同承担这些内容。每项材料应有当前说明作用或明确的后续作用。

**M**：

1. 先选择读者当前最缺的认识，而不是套固定目录：
   - 新对象未定位而需求已共享时，默认采用“对象类别与用途 → 使用者能做什么 → 核心 idea → 贯通案例”。
   - 问题、情境或本次范围尚未共享时，采用“必要问题/情境 → 本次范围 → 提出的 idea”。
   - 对象已知而报告主要支持一项判断时，采用“带范围的结论或建议 → 决定性依据 → 条件和限制”。
2. 将其余内容按实际理解依赖组织，例如对象与作用、问题与回答、条件与结果、证据与结论或方案对比；不把这些候选误作开头种类的完备分类。
3. 用一个贯通案例或图示走通需要解释的关键链。例子只说明其实际说明的关系，不能自动证明覆盖、性能或安全。
4. 原则上不保留状语，禁止连续堆砌形容词/状语。无必要信息的删；有必要含义的，写成对象、动作、条件或关系明确的短句。名称、技术术语和少数精度必需且指向清楚的限定可保留，但不能因“每个词都有信息”而保留修饰串。

**R**：Q.E.1提供对象定位的实例，Q.E.2提供对象—用途—评价关系的实例；是否采用它们，由父层P.2/P.5分配的当前说明责任决定。父层P.3要求充分性先于裁剪；P.5允许按情境选择入口，不规定唯一首句或章序。

**候选 implemented-by**：[SKILL-DRAFT §3](SKILL-DRAFT.md#3-选择开头和正文组织)、[§4](SKILL-DRAFT.md#4-让正文图表和案例共同完成说明)、[§5](SKILL-DRAFT.md#5-去状语去修饰堆砌写清关系)。尚需按本根目标对账，不因已有文件即视作批准。

#### D.3 — 对账并回改整篇报告

**Upstream obligation**：检查D.1与D.2的结果作为一篇完整报告能否共同满足P.1–P.5，而不以局部检查替代整体。

**P**：D.3必须分别检查：已写内容是否有当前贡献；必要内容是否已覆盖；正文、图、例子、引用和结论是否对同一对象、条件与证据状态负责；指定读者默认是否适合本稿读者前提且未被误用成固定模板。发现问题时回到缺少的D.1或D.2义务，不仅追加补丁句。

**M**：

1. 用 D.1 的说明任务逐项回看全文，检查对象、idea、关键关系、依据、范围和限制能否被找到并接回。
2. 检查每段、图表、案例和表述的说明责任；区分读者需要理解技术本身的困难，和作者遗漏指代、前提、因果桥、比较基线或证据状态造成的困难。
3. 对照来源核对术语、命令、数字、条件、否定和引用；保持设计、配置、观察、结果、目标和未知的区别。
4. 将发现回送给 D.1（任务/材料缺口）或 D.2（组织/表达缺口）并回改。无法解决且影响本次说明的缺口必须明示，不能用“稿件已完成”掩盖。

**R**：贡献检查不能推出覆盖，覆盖检查也不能推出每项都有用；二者及忠实性需要在同一整篇报告上复合检查。这个设计支持 P.3，但不证明真实 指定读者的理解速度，也不新增试读或审查 gate。

**候选 implemented-by**：[SKILL-DRAFT §6](SKILL-DRAFT.md#6-从整篇报告的位置核对)。该节仍是已有核对候选，不把存在这个检查段落当成效果保证。

### R — D.root 的论证与边界
