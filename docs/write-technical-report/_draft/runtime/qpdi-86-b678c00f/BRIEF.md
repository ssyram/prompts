## 父代理已经确定的理解与边界

- 终极问题是：以指定读者为重点读者，怎样写能快速传递idea的技术报告。写作技能是承载方法的产物，不是终极目的；本轮也不是继续设计Tool Auth Lang。
- “快”依前文指读者较少猜测、回补前提和重组关系，即更直接地理解idea，不是作者生成速度、字数更少、每篇固定分钟/页数。正确、充分的必要说明不能因此删掉；没有设过量化速度指标。
- 保留用户此前对通用方法的追求：不是只给某一篇稿打补丁，方法要能迁移。当前按“服务不同idea及相应沟通任务”理解它，不把所有技术体裁的完整写作法同时升成独立目标，也不否定其他体裁的研究能提供有用方法。
- 不把指定读者偏好当普遍科学定律，也不让它成为可忽略的附录。一般判断关系支配具体选择；在多个合格写法中优先其偏好，给可执行的条件推荐和例子。
- 正确传达、回应已明确任务不等于必须说服指定读者赞同，不能夸大能力或证据求认可；也不承诺满足所有读者的私人期待。
- 本轮是固定已有讨论和论证结构，不是再写一套庞大方法论、重新研究写作理论、强制试读或改技能实现。

## 主要内容怎么固定

### Overview与Q

先用人话说明真实问题、当前状态、这份记录的职责。QPDI是方法设计记录，不规定未来给指定读者的idea报告必须展示QPDI字段。

将用户本轮明确的目标作为正式锚点，忠实保留上述原句。Q.I只放用户真正追求/保护的结果，不把“先WHAT再HOW”“必须完整树”“固定章序”塞进Q。此前用户认可的信息充分、明确关系与少无效修辞，可以提供规范或推导来源；按其真实含义归位，不因为要填表就全部升成新Q.I。

尤其分清：内容采纳、事实证据、文件已写三种状态。只把用户确实明确的内容标confirmed；新的概括、排他边界、方法与推导标candidate或本轮工作解释，不因用户让落盘就自动定案。读者画像来自用户，可作为工作前提；不能把“用户确实这样说过”偷换成独立验证了指定读者的偏好。

Q.A只留实际支撑设计的认知前提，例如词义共有不等于新关系共有、读者背景影响解释深度、用户提供的指定读者画像。具体Tool Auth Lang的动机/tag已共享，只在该例的适用范围内使用，不推广到指定读者永远知道每篇报告的背景。

Q.E少量选真实已知的写作经验：V08先报手段但对象定位不足，V09补“规则语言”；7月9日范例用对象/输入输出/工程用途组织理解；补关系或完整图可能比删字更符合沟通任务。写清文本差异、用户评价与我们的推断，不编造真实指定读者试读、独立技能增益或普遍实验结果。不要重讲整段研发史。

### D.root与必要组件

固定能从现有讨论重建的候选D.root，给P、M、R与最少trace，不只把内容贴进Q/P/D桶。

- Root P应能判断是否偏离快速传递idea：所传idea及已接受目标/证据未被歪曲；读者能获得当前idea必要的对象、关键做法和关系；条件影响理解时已说明；表达省去无当前贡献的负担而不把解释转交读者；方法有可执行取法而不只有好文章的形容词。不同性质若已被同一条承接，不要换名重复。
- M可以从已有“确定此次需传达什么 → 组织内容和表达 → 整体回查并回改”关系收拢；不是固定写作流水线。每组件承接父层分配的contract，不另造Q。
- 在组件定义处就说明去向。能在本文件写完的就写完，并将已有SKILL-DRAFT相应章节标为候选落实/对账对象；有真实未闭合义务则明示，不假称已充分implemented。不因为Compose有厚设计模板就制造函数表、工具协议、数据schema或新文件树。
- 操作设计要说明输入来自何处，怎样得到这次idea必须交代的内容，事实缺口与多种表达候选怎样分流，怎样选择和组合表达、怎样回到整个任务核对。保持设计层，不重写具体prompt正文。
- 指定读者常用默认是：在需要时建立共同认识和对象定位，说明核心idea与关键关系，给贯通案例及当前判断必要的根据/边界。对方已知问题时不重复无作用背景；需要WHY/情境时可以先补。它是条件推荐，不是Q蕴含的唯一章序，更不是所有idea必须附同一套验收清单、性能数据或实现手册。
- 例子、段落、修饰词、图表从上述说明责任取得地位，不把它们各自变成独立终极追求。需要事实/技术细节才能讲通时保留；不要把“快速idea报告”变成禁止必要细节。
- R写清为何从Q得到P、M的组合怎样支持这些P以及未证明的部分。不要用每组件检查通过代替整体快速沟通成立，也不要宣称证明了实际指定读者理解速度。未测是证据边界，不是降低“快”的目标或新增测试gate。
- O只比较已有真实的做法，例如相同任务下“类别/用途先行”与“必要问题背景先行”的条件适配；不捏造选项、唯一最优或本质必然形式。
