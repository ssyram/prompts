# write-technical-report 修改方案

本方案调整现有技能的检查顺序与判据：**先确定报告任务和读者需要的联系，再补足内容，最后精简词句。** 保留现有的事实、范围、来源和否定条件检查，不新增调查、审批或读者实验流程。

依据与边界见 [综合报告](SYNTHESIS.md)。本文件是修改提案，尚未改动 `本地代理资料（未随归档提供）`。

## 1. 修改范围

| 现有位置 | 拟改动作 | 消除的具体问题 |
|---|---|---|
| description与开头总原则 | 从修饰词处理扩展到报告组织、关系与信息充分 | 技能的入口过于偏向句子润色 |
| §1 确认用途与材料 | 补入读者已知内容、本文任务及委托要求的区别 | 默认所有文稿都有指定读者式验收清单，或重复已知背景 |
| §4 组织正文 | 前移为新§2、§3，补具体定位与段落检查 | 先改词，再想文章如何组织；“按理解需要”判断力不足 |
| §2、§3 词句规则 | 合并整理为新§4，核心判据增加关系、作用及可解释范围 | 熟词被误当成清楚表达；只有删词/拆句的处理倾向 |
| §5 核对交付 | 保留事实与图文检查，增加读者能否确定对象、关系和任务的检查 | 文句正确、来源齐全，但文章仍无法理解或答非所问 |
| 参考记录与少量例子 | 补两个报告的开头对照及必要来源；更新有误导风险的旧例 | 把长篇研究直接塞进技能，或旧例继续缩小用户定制能力 |

名称与适用范围保持不变，不新建一套技能体系。正常使用不要求先读全部研究资料。

## 2. 拟采用的总原则

> 让目标读者知道本文在介绍什么、要完成什么说明或判断，并能把每项关键信息与已经理解的内容联系起来。每层先保证信息正确且够用，再减少没有必要贡献的表达负担。不要让读者替作者补出应由本文提供的关系。

“每层”不要求每段自含全部背景。相关认识可以来自前文、当前句子的说明，或有根据的读者共有知识。

## 3. 拟定五步正文

### 1. 确认读者、报告任务与材料

在现有§1上补充：

> 先明确这篇报告要让目标读者理解或判断什么，以及允许改变哪些内容。区分读者已经知道的内容、本文需要补充的内容、需要明确对齐的要求。
>
> 有明确委托时，保留其目标和关键要求；没有逐人约定时，根据文类及本文声明的问题与范围确定说明任务，不假设满足每名读者的私人目的。范围确实不清且会改变内容时才向用户确认。

保留现有的样文阅读、材料不足不编造、目标不降格、设计不冒充实测等条目。

### 2. 先建立能解释关键细节的联系

替换原§4的固定开头顺序：

> 开头先补足当前读者尚未建立的定位：对象是什么、承担什么任务、处在什么情境或流程中。不要只说“X采用Y”，却让读者猜X是什么、Y在其中做什么。
>
> 选择有辨识力且不会误导的类别，并交代本对象的关键职责。类别模板只用来提出有用问题，不强制填满，更不能据此补造功能。类别不明显时，可以先从问题、场景或职责建立位置。

保留一个小型入口表作为提示，而不是章序规定：

| 读者当前需要 | 可用入口 |
|---|---|
| 需求已知，对象未定位 | 对象类别、用途与关键职责 |
| 问题或本次范围尚不清楚 | 具体问题、必要动机与回应范围 |
| 对象的位置依赖陌生情境 | 必要场景及本对象在其中的作用 |
| 需要根据已有成果作判断 | 带对象、条件与范围的结果或建议 |

共有的WHY不用重讲；用于确认本稿范围的关键要求可以简短重述。方法信息可以进入开头，但其对象与任务关系须同时可理解。

### 3. 按各部分的任务组织并补足内容

将原§4的正文组织条目与原§3的关系说明合并，新增：

> 对每段先问：本段回答什么问题？理解它所需的对象、条件、因果或证据关系是否已经可得？读完后，读者是否仍须补做本段应提供的解释？
>
> 每项细节应回答当前问题，或为后文明示的需要提供前提；否则移出或删除。缺少必要内容时，先从材料补足；材料不能确定的技术问题不得为行文流畅而自行决定。
>
> 案例应走通需要说明的关键过程，图、配置、说明与结果之间要有可辨认的对应。需要时补汇合说明或完整图，不让读者自行拼装；已有联系不必反复解释。

段落顺序可以按包含、因果、时间、问题—答案等关系安排，不固定为一种系统分解顺序。检查可以反复修订，不要求单次五步走完。

### 4. 检查词句表达的关系与作用

将现有总问句改为：

> 这段表达让读者确定了哪个对象、关系或判断？它要求读者自己补出什么？目标读者能否从本句、前文或可靠共有知识确定其含义与范围？

保留原来的语义保护，补充以下处理：

- 修饰语不仅要有词义，还要明确它修饰谁、限制哪条主张、表达什么关系。
- 空泛评价有具体内涵时，把有依据的行为、比较对象或条件写出；含义未定时不自行选择解释。
- 保留必要限定、证据强度、句间联系和有依据的重点判断。将“称赞、强调……都不保留”收紧为排除只起造势作用、没有必要信息贡献的修辞，不误删结论或组织重点。
- 关系已经清楚的熟悉词块可以保留；关系不清时，可以移位、补关系词、列条件或拆句，采用最小够用的改法。
- 删除或改写后，检查对象、条件、范围、主张强弱及必要联系是否改变。词性、总字数、连续修饰词数量不单独决定取舍。

保留“只读”“同一次”“所有适用要求”“可能”等原有反例，不新增词语黑名单。

### 5. 从读者位置核对并交付

保留原事实、功能、因果、条件、数量、否定、证据状态、图表与引用核对，增加：

> 读者能否从开头判断本文的对象、任务和范围？关键细节能否接回已建立的内容？正文是否交付了本文承担的说明，而不只是列出话题？
>
> 区分需要读者思考技术本身的困难，与作者遗漏指代、关系或前提造成的困难。修复后者，不以“内容本来复杂”作为省略解释的理由。

仍只交付文稿及必要说明，不附完整方法论；不以字数下降或词频下降证明可读性提高。

## 4. 例子如何调整

仅补足三个实际问题，不扩成庞大例库：

| 问题 | 拟采用的例子 |
|---|---|
| 对象尚未定位就讲手段 | 用V08/V09开头对照：先明确规则语言及使用关系，再讲标签与树；不把“下一代”这一修饰词本身当定位方法 |
| 信息缺少而非字数过多 | 对比“自动附着文件标签”与承担机制说明任务时必须交代的文件引用、路径、配置匹配和落点 |
| 词块有义但关系被遮蔽 | 引用NASA短名词块与长名词串的对照，说明补关系词也是选项，不必全拆短句 |

现有“更灵活”的Tool Auth Lang改写例可更新为：

> 用户可以定义识别、构树、标记和审核规则，也可以加载内置规则套装。

这使用本项目已经明确的能力，避免旧例只展示补充限制而继续诱发能力误分。换项目时仍须回到该项目已有事实，不能照搬这些能力。

## 5. 不加入技能的内容

- Grice、Miller等理论名称及其争论过程；只把成立的操作要求写入技能，出处放参考记录。
- 固定CARS章序、固定摘要字数、固定WHAT→WHY→HOW、每段都要系统输入输出。
- 所有比较都量化、所有修饰语展开、所有长句拆短、所有已知术语反复定义。
- 强制真人复述、A/B测试、独立审查gate或新的调研步骤。
- 从“作者—读者契约”继续推导未经用户要求的新义务。

**实施边界：只在确认后修改技能及其参考材料，不改Tool Auth Lang方案、原报告和历史证据。**
