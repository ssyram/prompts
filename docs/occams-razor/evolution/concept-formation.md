# 从 callgraph 单案例的三层分析到 `X|F`

本文只概括概念形成的关键中段，不是独立证据账。逐有效消息、并行会话顺序、工件快照及未闭合问题见 [`archaeology.md`](archaeology.md)。

## 1. 前史只提供待解决问题

项目最初针对 AI 的层次错位、无根据概念增殖、过度编排和细节固化。早期 SKILL 陆续加入对象边界、删除反事实、逐层理由、意图推断和有限具体化。

这些规则有实际内容，却仍主要来自失败样本。它们没有共同回答：必要性相对于什么、对象自身规定怎样参与、删后必须保持什么，以及为何同一判断能递归到每一层。

在进入关键案例前，讨论已确认四点：结果必须必要而仍充分；整组自我支撑内容可以一起删除；判断位置必须有根据；具体列表和实现不能替代上位原则。这些是后续分析的材料，不是已经完成的体系。

## 2. 一个 callgraph 规格同时出现过度与不足

一项 callgraph 规格工作只收到普通自然语言的 Occam 要求，没有加载具名 SKILL。

第一轮设计把它扩张成自足信息库：除调用边外，还试图承载位置证据、未知项、变化状态和其他语义。用户重新指出实际用途：下游主要需要统一、稳定、可查询的内部调用关系；已有权威来源负责其他语义。大量字段因此失去消费者。

但压缩后的另一稿又偏到相反方向：它花很多篇幅解释全流程和方案合理性，却没有明确实现者真正需要的数据合同与操作接口。内容变短并没有让对象充分。

这两种失败迫使判断从“字段看起来是否多余”转向：

```text
这个对象为什么被需要
→ 它实际承担什么职责
→ 实现者为了履行职责必须得到什么
```

## 3. 第一次逐层拆解：问题不能直接推出字段

用户先问：callgraph 何以被需要，它成立的辩护是否直接决定其本质内涵。

分析将问题拆成三层。

### 3.1 问题先规定所需能力

不能从“callgraph”这个名称开始，再为既有设计补理由。应先检查下游真正要求什么。该案例需要的是一种统一、可重复查询、能反映已确认调用关系的能力。

到这里仍不能推出必须使用某个 JSON 文件、某组操作或某些字段。必要性辩护也不只来自缺口；正向能力、定义性要求和现实约束都可能使内容必要。

### 3.2 具体方案必须另行取得位置

问题通常只规定能力和性质，不能唯一推出具体方案。候选方案有自己的能力、限制和内部结构；它必须证明自己能够承担要求、与现有约束相容，或者由用户明确固定，才进入当前设计。

这一步属于方案选择与综合。Occam 可以检查已经给定方案中的内容，却不能假装删除动作已经替用户完成了非等价选择。

### 3.3 字段必要性属于选定方案内部

方案被接受后，上层要求与方案自身规定共同形成局部 contract。只有这时才有资格问字段是否必要。

在该案例中，调用边和稳定端点直接服务查询；重复其他权威来源的节点语义、逐调用证据、无消费者的来源记录和变化历史则没有同等理由。生成、查询和确认后更新等操作是否需要，也取决于实际消费方式，而非“callgraph 通常有什么”。

所以完整关系是：

```text
问题规定
→ 所需能力
→ 方案选择
→ 上层要求与方案自身规定形成局部整体
→ 内部字段和操作接受必要性判断
```

## 4. “自在—他在—新整体”：单案例的第一次哲学抽象

用户进一步提出：问题已有的规定可以称为“自在”；具体方案不是由问题唯一分析出来的，相对于问题最初是一个“他在”对象。问题要求与方案自身规定相遇后，才形成方案在当前设计中的具体内涵。

当时的结构可以整理为三个环节：

```text
当前问题作为已经规定的整体
→ 候选方案作为尚待引入的外部对象
→ 二者经过需求、能力和适配辩护形成新的具体整体
```

这不是简单相加。问题只规定方案必须做到什么；方案只能以自己实际拥有的方式承担；二者相互限制后才形成当前 contract。

### 4.1 新整体会成为下一层的“自在对象”

用户随后把这套关系推进为递归模型：

- 一个方案在父层是待引入的“他在”对象；
- 它一旦被选择并与问题要求形成具体整体，在子层就成为已接受的“自在”对象；
- 它的字段、模块和操作成为下一层待裁决内容；
- 若要质疑方案整体，就提升到父层，而不是用字段之间的依赖反证方案必要。

这一步已经包含后来“局部整体—内部内容—逐层重落根”的核心结构。

### 4.2 术语受到过哪些修正

“问题自在—方案他在”不是严格的黑格尔固定二元组。当时的批判保留了设计关系，同时收窄哲学主张：

- Q.I、事实和经验共同规定当前问题；“自在”不是从价值中立事实推出规范目标；
- 具体方案不是问题概念的必然展开，也不保证唯一或全局最佳；
- “不圆满”只是必要性的一种表现，不能再次把所有必要性缩成缺口；
- 当前最小性只相对于已接受层级成立。

因此，本文用“自在/他在”记录当时实际使用的过渡语言，不把它报告成黑格尔原典结论。今天称其为“三层论证”可以帮助理解，但当时源记录没有使用“三段论”这个名称。

## 5. 第一次 QPDI 编译，以及一次删过头的自应用

完成上述分析后，用户认为材料足以进入详细 QPDI。首版设计写入：有根据的工作理解、问题与方案的条件关系、逐层必要性、Sound/Complete 护栏、Concise 和递归。

随后对这套新设计自应用 Occam。为了不让近期高频词取得永久地位，设计删除了 callgraph 案例、“自在/他在”、固定图、清单和多种过程表达。

删除案例与哲学术语本身可以成立；但这次同时把它们承载的关系删弱了。用户立即指出两个缺口：

1. Occam 的本质是分析性排除，不负责替用户综合新的非等价方案；
2. 同一判断在每个已接受复合对象中重新成立，这种递归不是可选流程，而是全局性质。

于是 Architecture 补回分析性 C2、本质递归和 Sound/Complete 边界。这个事件证明：**去掉形成过程的词，不等于可以去掉由这些词发现的规定。**

## 6. 从三种合法性到当前层的两步操作

补回分析性和递归后，用户仍认为“先形成工作理解”不够。继续分析得到三种不能混同的关系：

```text
工作立场的合法性
→ 为什么采用这个问题解释和判断标准

方案进入的合法性
→ 为什么这个具体方案有权承担问题要求

内部内容的条件性必要
→ 方案进入后，哪些部分对当前局部整体必要
```

第一项不能被“用户意图”四个字包办；它要有授权、事实、作用域和可实现性。第二项不能从“需要某种能力”直接跳到“需要这个载体”。第三项才属于方案内部的 Occam 判断。

用户再次把 callgraph 字段拿来检查：若当前正在分析字段，前两段辩护其实已经封装成 callgraph 方案的完整局部前提。字段层不必重演全部历史，只需：

```text
取得足以裁决当前字段的完整局部前提
→ 相对于该前提判断字段
```

这里的“完整”只指会改变当前裁剪的全部有效规定，不是全部项目历史或方案的一切性质。这同时明确了初始 SC 边界：Occam 可以维护并检查删后充分性，却不能凭删除补造原对象缺失的内容。

## 7. “父结构”在这里才出现

完成字段层的两步折叠后，用户第一次用“父结构”概括当前完整对象：

```text
父结构为何被当前需求接受
+ 父结构自身已经成立的性质
→ 父结构在该需求下的内涵
→ 判断其内部内容
```

这个词不是早期 callgraph 的随手命名。它是对前述“问题自在—方案他在—形成新整体—下一层递归”的进一步压缩：到了内部字段层，先前的选择与适配已经凝结成一个承载局部 contract 的整体。

用户没有停在这个概括上，而是立即批判它的普遍性：

- 父结构似乎预设当前对象是某种解决方案；
- 顶层分析是否还需要一个更高父结构；
- 纯研究、表达或行动压缩是否都具有 `Q → S → S.parts`；
- “父结构”究竟是对象、语境还是二者的混合。

这个自我批判直接制造了下一步所需的区分。

## 8. `F / X / X|F / x_i`：从设计特例中抽出普遍角色

AI 在回答“父结构是否普遍”时，把 callgraph 案例里重合的角色拆开：

- `F`：有权规定本次判断的语境；
- `X`：当前被分析的完整对象；
- `A(X)`：`X` 已经成立并与当前判断有关的性质；
- `X|F`：外部规定与对象自身性质共同形成的完整相关内涵；
- `x_i`：`X` 中接受保留或排除判断的内容。

这组符号没有否定此前三层分析，而是抽掉了它的设计特例：

| 单案例中的规定 | 普遍角色 |
|---|---|
| 当前问题、用途、事实、约束及其适用根据 | `F / J_F(X)` |
| 在当前层已经形成的具体整体 | `X` |
| 方案或对象自身实际相关的能力与限制 | `A(X)` |
| 问题要求与对象性质形成的局部 contract | `X|F` |
| 字段、模块、段落或其他内部内容 | `x_i` |
| 新整体成为下一层已接受对象 | 递归重落根 |

用户下一回合立即认出：“父结构”与 `X` 外延相同；相对于内部 `x_i`，`X` 本来就是它的整体。`X` 更精确，只因为它不额外暗示方案、永久层级或顶层父项。

AI 随后把讨论扩张到“`X` 是否应在最终结果中存在”；用户指出这不是当前命题。撤回这条扩张后，稳定关系才是：

```text
F 怎样规定对 X 的判断
+ X 自身已经成立的相关性质
→ X|F
→ 判断各 x_i 是否必要
```

所以，`X|F` 的出现确实是一回合完成的关键统一；它之所以有力量，是因为前面的单案例分析、哲学抽象、第一次编译、误删、恢复和父结构自我批判已经把角色逼到临界点。

## 9. 闭合以后：框架开始纠正自己的 prompt

用户要求以 `F → X → X|F → x_i` 为 Architecture 中心，再重写 SKILL。由此新增了对象自身规定 `A(X)`、适用根据 `J_F(X)`、统一删除证明和结构性失败模式。

第一次编译又把近期讨论平铺成过多 pattern，并把 `X` 重新写成“被语境需要的方案”。用户要求反思；设计随后把失败项归并回根关系，并把 `J_F(X)` 改成“`F` 凭什么支配对 `X` 的判断”。

这次自我纠正发生在 `X|F` 之后，与第 5 节那次删过头不同：前一次误删了尚未抽出的本质关系；这一次则用已经形成的关系压缩其运行时实现。

## 10. `F` 成为第二个独立转折

虽然 `F` 已在中心模型中，最初实现只要求从材料中“取得”意图、事实、约束、用途和作用域。用户指出，这仍允许模型把生产对象时的开发语境搬进对象实际被使用的语境。

`F` 的形成经历三次关键否定：

1. 假设生产过程消失后还剩什么，只能测试脚手架，不能正面形成 `F`；
2. 罗列问题、事实和成败边界仍是声明式成分表；
3. 真正动作应围绕用户给定的 `X`，从其局部用途接回仍有效的中间目标和最终目标，再核对当前事实、约束和完成条件，清除已经失根的过程历史。

另一个长期使用的重校准工具提供了有限正面经验，但被明确视为不完美。因此设计只吸收其动作，不把它当正确性保证。

`X|F` 说明为什么 `F` 是高杠杆位置：它的错误会改变多个内部判断。但这只推出每次都要检查语境是否够用，不推出投入越多越好。若不同的合理语境解释会改变当前裁剪，就继续核对；若结论相同，就停止。

## 11. 当前框架与一句调用语的最小对比

| 形态 | 能做什么 | 核心缺口 |
|---|---|---|
| 一句自然语言调用 | 唤起模型已有的 Occam 印象 | 没有说明判断根据、对象内涵和删除证明 |
| 早期经验规则 | 提醒检查对象、理由、递归和停止 | 各条仍缺共同的生成关系 |
| 现行框架 | 从 `F` 与对象性质形成 `X|F`，再统一判断任意内部内容 | 跨领域执行稳定性、记号唯一性与理论完备性仍待证明 |

最强而不过界的结论是：

> `X|F` 比早期框架更正确，不是因为它更新或更复杂，而是它保留了单案例三层分析中真正起作用的关系，同时删除了“当前对象必须是解决方案父结构”这一不普遍的附加前提。它是否是终极、唯一答案，仍保持开放。
