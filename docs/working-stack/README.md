# Working-stack：研发沿革与使用依据

Working-stack 是用户拥有、AI 协助维护的工作状态：整体目的是什么，当前注意力放在哪里，为什么深入这一层，满足什么条件才能返回。它以带稳定 ID 的帧树保存责任与历史，以一条活动路径表示当前工作栈。

本文记录这套方法如何从实际讨论中形成，不另立一套规范。可直接使用的版本见 `current/working-stack.md`；这里解释其来源、修订理由和证据边界，而不是复制完整提示词。

**重要的研发历史实物**：[用 working-stack 开发 working-stack：去敏工作栈](working-stack-history.md) 保留这条方法讨论线的原则、帧树、事后更正的父链、逐帧达成情况和原则去向。它记录当时怎样推进与修正，不替代现行方法，也不是原始会话的逐字副本。

## 证据与状态口径

本文只使用以下来源类别，不保留私人定位信息或原始对话转储：

- **用户决策**：原始长会话中相关用户发言，包括上下文压缩前的目标描述、压缩后的纠正，以及最后的发布指示。按顺序流式检索；重复发言不算独立证据。
- **观察到的工作栈工件**：一份实际讨论栈和一份方法讨论栈，分别保留工作目的、计划、局部完成记录和原则演变。它们是状态记录，不是独立正确性证明。
- **现存方法文本**：本地方法文件与仓库当前可复用提示词，用于确认规则已写入文本，不据此声称实际使用始终遵守。

下文区分提议、纠正、明确采纳、文本落地和仍未闭合的事项。其他方法的研发文档仅提供“问题—理由—经验—边界”的写作参考，不为 working-stack 增加上位规则。

## 1. 起点：恢复决策位置，而不只是回顾时间线

早期用户要求的是一种**决策推进回顾**：从最终目的，经已选定的具体方案，恢复当前正在解决的问题，并知道完成后继续哪个计划项。抽象原则不能代替具体决策，最近发生的事情也不能代替当前责任。用户同时要求固化讨论中的需求、理由、方案和决定，并保留已经完成的事项。

随后，在深入理解执行过程的讨论中，用户更明确地提出注意力问题：追问会不断深入，人需要一个稳定路标，随时能把注意力放回一个核心问题，并在讨论完后知道下一步。工作栈因此不只是给 AI 管任务，也是给用户维护可返回的思考位置。

这一阶段用户给出的结构已有根计划、局部理解任务、更深的具体问题、各层 FOCUS 和返回条件；**完整字段表、文件布局、原则处置和 expired 语义并非一开始就齐备**。

## 2. 关键演变：提出什么，又纠正了什么

以下阶段按用户发言先后概括；“写入”只表示在当前工件或方法文本中可见。

| 阶段 | 提议、纠正与理由 | 采纳／落地边界 |
|---|---|---|
| 决策骨架 | 区分支持某方向的原则与该方向下真正选定的方案；每层交付要服务上一层，而非只列最近工作。 | 用户明确要求；后续持续要求保留已完成项和已作决定。 |
| 注意力路标 | 另设方法讨论工作线；有意义的深入与返回主要用 push/pop，没变化的对话不必更新。 | 用户确立方向。方法栈一度只是空栈加全局原则，不能虚构正在做的任务。 |
| 帧的最小责任 | 计划、FOCUS、局部原则、弹帧目标，以及 pop 时的达成辩护；push 相对宽松，pop 必须核实。 | 用户纠正了过度抑制 push 的理解；后来再次强化为非微小计划项默认 push。 |
| 树与历史 | 每帧有稳定 ID，已 pop 帧仍连接父节点。早期曾讨论原则 release 或 delete，后来明确要求不删原内容，只标去向。 | 保留历史取代直接删除；工件也标明部分父节点是后来补建的逻辑结构，不冒充过去已实际 push。 |
| 文件化与副作用 | 两条工作线显式保存全文，增加实际外部影响；短回答可以累积后再写。 | 双文件与独立本地版本管理是当时的实例约定，不是所有工作线的强制安装方案。 |
| 压缩后恢复根目的 | 用户指出实例标签遮蔽了原本“理解执行、形成分析并反馈改进”的目的，要求回查压缩前描述；父计划不能用子帧编号代写。 | 工件恢复目的并记录修订。来源字段帮助说明每帧为什么存在，而不只留下近期产物。 |
| 栏目与可读性 | 简短不能靠隐藏原则、计划和完成情况获得；分清结果、确立原则、可自命名备注与外部执行事项。 | 用户明确同意分类调整；工件保留误分类条目的原身份与 `reclassified` 记录。 |
| 从实例到方法 | 全局原则清单不足以构成可用方法；过短初稿漏掉采用时机、维护全程、liveness、用户协作和例子。 | 实例整理与整体方法成形被分成不同帧；现存方法已包含完整使用周期，但两者的完成不能互相代替。 |
| pop 语义细化 | 增加“原目标不再重要”的 `expired`；否定把所有未完成或被证伪都等同过期的假设。达成情况最终要求结果、目标对应、判断依据三项。 | 写入现存方法。返回后的工作要在回复中告诉用户，不混入达成情况字段。 |
| 后期发布与返回 | 早期保留发布决定；后来用户放行发布，并要求逐帧检查方法栈，再返回原讨论。 | 提示词随后已单独提交、推送；方法栈的剩余帧再逐帧核对并关闭。这是不同时间、不同证据支持的两项交付，不能从发布授权直接推出它们。 |

来源：用户决策；上述字段、修订痕迹与开放状态另由观察到的工作栈工件、现存方法文本交叉核对。

## 3. 为什么形成现在的字段模型

帧是一个有目的、可返回的工作单元，不是一条聊天消息，也不是一次工具调用。

| 内容 | 作用及形成理由 |
|---|---|
| **ID／上帧** | 保持身份和父关系；pop 后仍能回查。活动路径是栈，连同已弹节点的整体是树。 |
| **来源** | 说明为什么建立这一帧。根帧与独立旁支尤其需要交代存在理由；普通子帧说明使父工作暂挂的问题。来源不等于目标，也不只是路径引用。 |
| **弹帧目标** | 定义返回条件，防止把“计划都勾完”当成“责任已完成”。子帧目标应细化父目标，而不是复制它。 |
| **计划／FOCUS** | 计划陈述本帧自己的工作；FOCUS 标出当前项。父计划写实际责任，子帧链接不能代替责任描述。 |
| **达成情况** | 仅 popped 帧需要，紧接弹帧目标：结果是什么、怎样对应目标、凭什么这样判断。它不是流水账，也不是返回导航。 |
| **已得结果** | 保存对本帧目标有贡献的非平凡收获。学习本身可以是目标，因此有依据、获用户认可的理解也可以是结果。 |
| **确立原则** | 保存用户明确确认、后续须遵循的局部规则或临时设计决定。重要事实、AI 推断、命令句措辞本身都不产生规范效力。 |
| **备注** | 保存值得留下但不属于上述栏目的事实、背景、认知或待核判断；可有多个具名备注，并标明证据状态。 |
| **外部执行事项** | 独立记录实际副作用，如修改工件或改变进程状态。它与结果分类是两次判断；只读研究有结果，也可能没有副作用。 |

文件先说明整条工作线的目的，再给活动路径概览；正文先列从根到顶的活动帧，后放 popped 帧。概览只在最后一项标 TOP 或 PAUSED，不展示虚拟栈底或混入历史节点；正文标题另有各自状态。暂未归属的非平凡内容可以缓存，但缓存不等于已确立原则。

来源：用户对结构、局部性和栏目含义的连续纠正；观察到的工件布局与现存方法文本。

## 4. 如何推进而不失去活路

这里的 **liveness** 指工作状态有可辨认的下一步或具体阻塞，不承诺自动推进必然成功。

1. **先恢复目的。** 从原始委托、有效用户纠正和已接受决定恢复当前栈，区分想做、做过、验证过与接受过。不要另起一份栈覆盖既有状态。
2. **再决定是否记录、记在哪。** 筛出非平凡内容，放到目标最相关的帧；分别判结果、原则、备注，再独立判断外部副作用。不因内容重要就给所有祖先重复记账。
3. **非微小计划项默认 push。** 给子帧来源、FOCUS 和弹帧目标；微小推进可以只更新当前项，例如核对一处已知材料或修改一句措辞。不是“尽量少 push”，也不是每个工具调用必建一帧。用户修订后的目标与计划不能被 AI 随意改写。
4. **保持出口。** 当前顶应指出正在做什么；不能行动时，指出缺谁的哪项决定或哪份证据，并继续不依赖它的已有工作。计划耗尽但目标未达，可短暂 push planning 帧，找出有依据的后续计划后返回；不能虚构 done 或靠无目的重复审核制造进展。
5. **核实后返回。** 子帧完成不自动证明父计划项完成。pop 时核对目标，保留历史，并告诉用户返回帧的状态、FOCUS 和下一项，必要时建议继续 pop。
6. **停止前轻量维护。** 检查栈顶、根目标、返回条件和下一步是否仍相连；有实质变化才更新。短讨论可先在会话中记下拟更新内容，再合并写入，不要求每句话产生文件改动。

源于主线但不属于其完成义务的独立话题，可在用户确认后作为 `[digression]` 保存来源与返回路径；普通子任务不能借此逃避父目标。AI 可以建议建栈、push/pop 或处理旁支，但该方法不授权它改换用户目的、扩大执行范围或自行启动实验。

来源：用户决策与现存方法文本。这里陈述的是已形成的方法，不是对早期每次操作的合规断言。

## 5. Pop：完成与过期不是同一个判断

- **完成**：弹帧目标已达，达成情况给出结果、对应关系及判断依据。
- **`expired`**：用户确认原目标已不再重要，因此退出；不是 done，不等于事实为假，也不是“凡未完成皆过期”。
- **仍重要但未完成**：留在工作状态中，补计划或指出阻塞，不能假 pop。

匿名例子：`[W-02]` 若以“判断某断言是否成立”为目标，可靠反例可以完成该目标；若以“证明某断言”为目标，反例并不完成证明。只有用户确认原证明目标不再值得继续时，后者才可记为过期。

每次 pop 回顾已弹出的下层子树，只增加对本帧目标确有贡献的联系、关键结果、原则或副作用摘要，也可以引用子节点 ID。不覆盖原记录，不提前在活动祖先中编写下层总结，更不把同一内容逐层复制。最重要的汇总用途之一，是说明子工作怎样支持本帧的达成判断。

来源：用户新增条件、随后对“被证伪即过期”的纠正，以及现存方法文本。

## 6. 局部原则如何成为更大范围的约束

最初的 release/delete 想法后来被历史保留要求取代。当前模型保留原原则及其身份，并记录处置：

- `released → <接收处 ID>`：有明确接收位置，说明它在哪个更大范围继续适用。
- `kept-local`：保留在原帧，不向上推广。
- `invalidated`：已被推翻，保留理由。
- `reclassified`：原本是事实或认知，却被误列为原则；移到合适结果或备注，保留原身份。改类不等于判事实为假；若曾 release，还要同步接收处。

方法讨论栈中的“全局”是相对于当时讨论的维护方法而言，不意味着每个局部实验结论都约束所有项目。pop 是审视推广范围的时机，不是自动升级权限；过期帧的原则尤其不自动上移。用户明确确认才建立规范效力，沉默、继续聊天或 AI 自称完成都不能替代确认。

来源：用户对保留内容、原则分类与推广的决定；工件中可见的重分类和接收处修订。

## 7. 实际使用学到了什么

这些是本次使用暴露的问题与修正，不是普遍有效性的统计结论。

- **有栈仍可能丢失目的。** 压缩后，运行标签曾取代原本的分析目的。用户要求回查早期发言以纠正；持久化能支持恢复，但不保证正确恢复。
- **有文件不等于有方法。** 文件整理完成后，用户仍指出方法初稿过短，缺完整生命周期。实例维护、方法成形和发布是不同交付，不能借前者的完成证明后者。
- **事实容易被误写成约束。** 现存工件确有原则改类及上层接收项修订；保留身份与去向使错误可追踪，而非静默抹掉。
- **学习成果有局部验收边界。** 讨论栈记录了用户认可理解并要求 pop，也明确某次只是粗略达成，不代表整体工作验收。
- **历史结构也可能是事后整理。** 工件对补建逻辑父节点作了说明。更清楚的树结构可以帮助阅读，但不能倒写为当时已执行的操作。
- **维护成本需要节制。** 每层重复副作用、把返回导航塞进达成字段、为短回答立即写文件，都不等于更清楚；局部记录、pop 时建立关联、合并更新回应了这些问题。

来源：用户纠正与观察到的工作栈工件。它们支持“发生过这些问题并形成修订”，不证明方法消除了焦点漂移、提高了速度或保证所有推断正确。

## 8. 尚需用户判断与证据限制

**历史状态不能压成一个“完成／未完成”。** 方法栈的中途记录曾把整体方法成形列为待确认；后来用户放行发布，提示词已单独提交并推送。用户随后要求逐帧检查剩余方法帧，完成后本地方法栈为空。中途待确认、实际发布、方法栈关闭各有独立依据，不能互相代替；这些事实也不证明方法的跨任务效果或所有运行环境均已自动加载。

目标是否仍值得继续、具体 pop 的确认、哪些局部原则应推广，以及新增规则的采纳，仍由用户决定。方法提供提醒、记录和建议，不代替这些判断，也不是额外审核轮次的授权。

本次材料来自一条长会话及其相关工件；没有跨任务对照、长期效果测量或完整安装验证。本文采用概括转述和匿名例子，省略私人路径、身份、运行标识、专用代码及无关提示词。原始材料与公开表述不做逐字映射；无法安全表达或不能核实的细节不作事实主张。
