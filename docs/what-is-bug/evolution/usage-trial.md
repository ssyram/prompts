# 首次使用测试：筛选旧 PR review

## 设置

在现役正文发布后，用一个独立上下文的 GLM-5.4（max）分析此前已经提交的 PR review：正文与25条逐行意见。用户要求采用面向项目作者的严格Bug论域，由主代理检查模型输出。

模型收到内嵌的现役正文、旧review和原实现版本。历史报告及审计者后来添加的测试均为被审证据，不具有规定原作者义务的权威。

本次测试发生在发布之后，不回写为早期讨论已得出的结论。没有重新启动全仓找Bug、修改产品代码或更新线上review。

## 模型成功区分的部分

- 当前代码正确，修改实现后新测试能发现变化：归为防回归建议，不能据此证明当前运行Bug。
- 仅存在panic处理分支：没有给出合法触发路径时，Bug论证未闭合。
- “释放失败不报错”与“仍输出诊断”：还需要厘清“不报错”是指判定结果还是诊断输出，文字不同尚不足以认定冲突。
- 注释 `including heartbeats` 有“心跳也算使用”的相容解释，不能只选不利读法认定写反。
- 对没有回源的条目如实列为未覆盖。

## 主代理纠正的两项判断

### 1. 启动排队与20秒超时

模型认为模拟中长时间阻塞A，足以对应真实启动的长耗时，并主要把问题归为触发频率未测。

核对原实现发现：测试暂停的是假的 `HostFacts::spawn_facts`；真实 `ProductHostFacts::spawn_facts` 的两次宿主HTTP读取各有请求时限。把总启动预算设成120秒，尚未证明这个被暂停步骤可以形成同样的20秒等待。

这不否定其它长启动路径，而是要求原证明为其模拟条件提供对应根据。另有设计文本明确区分20秒判定等待和120秒后台启动，“多等一会儿”未明确承诺当前判定一定成功，因此文档冲突也须进一步论证。

**本次结论：原论证未闭合；频率低不是排除Bug的理由。**

### 2. 换运行密钥后，裁判进程触发普通hook

模型认可换密钥后旧标记失效的机制，又把“是否应绝不创建actor”交给作者补裁决。

核对实验发现：使用的是返回500的假daemon，观测仅为连接次数，未实际创建actor或验证残留影响。原代码注释描述已验证标记时的跳过行为，并规定验证失败走普通路径；单凭该注释，尚不足以推出跨daemon重启也须持续豁免的义务。

**本次结论：机制有证据，原Bug判断仍缺规范和后果根据。**SKILL附录案例只能帮助理解，不能作为被审系统事实的证据。

## 可保留的文档证据示例

主代理回源确认了几组具体关系：

- 修复文档标明验收表已同步，验收表仍写被新机制拒绝的静态值；
- 同一设计文档对 `LOG_POLL` 分别给出50 ms与100 ms，代码为100 ms；
- 审计字段旧句概括为全部为空，同文细化规定已知作用域照填。

这些结论的对象是具体文本关系，不由此扩展成整个系统存在运行缺陷。

## 结果与限制

此次试用部分有效：模型能够按规范区分建议、事实和Bug证明，但在模拟代表性、注释的规范效力、附录案例的证明资格上仍会越阶。

主代理的核对报告保留了原模型结论和修正理由；未逐项核实的材料保持未覆盖。现役正文未据此自动修改，本次也不是对原项目“没有Bug”的证明。
