# What is a Bug：发生记录

## 范围与来源

本记录整理当前会话可见的讨论。原始材料为用户消息、助手答复及同时期可见的执行回执。详细讨论见[讨论记录](../../../what-is-bug-discussion-log.md)。下述早期工程背景来自同一会话前段的摘要整理，详细讨论记录从用户提出 Bug 报告应包含的内容开始。

省略工具回显、自动通知、重复加载的资源全文；保留连续纠正及重复发送的实质消息。个人账号与本机路径脱敏。本文没有声称覆盖其它会话或双方未公开的思考。

## 1. 原始动因：给项目作者的 PR 审查意见

用户最初要求了解一份较大的 FSM 工具 PR：改动让 Stop、Watcher、Review 在判定时通过专用工具按需读取证据，并引入 OpenCode 的独立 judge server。随后要求用细粒度检查与内部一致性审查找跨组件问题，指定 GLM-5.4，并要求不改产品代码。

助手派发了代码、文档和测试相关的分析任务，报告把文档差异、运行行为、测试缺口和其它维护观察一起汇总。用户要求先整理成决策项与非决策项，再给项目作者可读的 review。

用户继续要求为可实证的意见补证据。助手新增测试，并通过临时修改实现观察测试能否失败，后又把意见发为 GitHub 评论和逐行 review。此阶段用户多次要求：问题与证据分别说清、用人能懂的词、规范意图要有出处、代码问题要核对作者已作取舍。

当用户询问“环境变量名无跨语言守卫”“client 二进制名字面多处无守卫”为什么值得提交时，助手分别以实测和静态推演解释，随后撤回部分意见。之后用户进一步指出：测试缺口与实际 Bug 的关系仍然没有论证清楚。

本段只记录当时报告与操作的发生，不把助手当时的“已证实”声称作为这些 Bug 当前成立的证明。

## 2. 报告表达与判断依据的连续质疑

用户要求每条 Bug 讲清场景、原意、合法可触发过程及后果，并要求意图有文档或清楚标明的常识依据。

助手先把“系统应串行处理以保证互不干扰”写成意图。用户指出它混合了用户期待、当前设计与设计代价；合理叙述应分别交代：用户期待、作者选择串行、作者接受等待、实际超出该代价的情况，以及后果。

用户接受后来一版的表达方式，并授权替换线上 review。后续又限定措辞应沿用已确认文本，必要术语要解释。

## 3. 重启场景争议与先总结教训的暂停

项目作者通过用户质疑：正常停止 server 是否先关闭 judge。助手核对停止、重启、Claude Code 判定子进程与 OpenCode judge server 的关系，随后几次改变该意见的定性。

助手一度将其描述为需要决定是否接受的行为，后又称为可接受的冗余。用户追问“接受啥”，随后指出：它不是值得记录的明确 Bug，要求先总结失败原因，待确认后再筛选原意见。

用户接着提出更一般的问题：场景可能根本不可达，助手可能伪造了一个可触发的 Bug；“程序被修改后新测试能发现”也不能直接证明原程序已经存在 Bug。

## 4. 从工程个案转向广义定义

用户明确提出三元组：意图、可达、后果，并说明工程合法性判断常用顺序为文档规定、代码允许、保守的常识兜底。文档明确排除的输入应按排除处理；未明说的情况需要结合适用限制与真实调用方式论证。

助手先写成项目工程规范。用户纠正：讨论是广义原则，不是该项目的工单标准。

助手又将“更安全、更规范”绝对称为伪意图。用户纠正：它们能否入域取决于讨论论域；严格与宽泛约束的是可纳入的内容。

用户进一步区分论域与严格度：论域可定制；严格度是对论域取值的限定标准。助手曾要求各维度同步收放，后续讨论没有保留这一要求。

## 5. 对定义、论证与二阶判定的澄清

用户说明：论域通过意图、合法入口、后果判定三个投影体现；Bug 判断的逻辑结构固定，所取论域变化。

用户连续纠正：

- 意图是想做什么本身，来源是佐证；
- 后果包含性质、程度及可接受性；
- 推荐用于排除是常见用途，不是能力边界；
- 本 SKILL 主要检查一项 Bug 判定是否合法，而不是给出固定的一阶判定程序；
- 论证形成可以是辩证的，论域和授权内容在讨论中逐渐显露。

随后采用“规范意图”一词。用户要求先干净陈述抽象定义，再写论证的认识论、推荐方法论和可调整模板，解释与纠偏放 Q&A 或附录。

## 6. 哲学讨论与任务边界修正

用户邀请从康德、黑格尔等哲学角度分析框架。助手讨论判断资格、内在批评、规范承诺、实验前提及对象问题与论证充分性的区别。

用户逐项确认、修改其位置与用途：

- 宽松放宽论域，逻辑要求保持，放 Q&A；
- 授权根据与作者是否同意报告的区别，放 Q&A；
- 非明言推导可从常识怀疑出发，需继续形成辩护；
- 合法性的重要困难是说明候选路径未被适用规定排除，不是套数学 completeness 标签；
- 是否修改不属于 SKILL 范围；
- 辩证运动说明放附录，正文检查运动后形成的论证；
- 文档冲突宜以“共同适用、内容不相容”组织，而不是拿若干核对问题声称全面；
- 二阶检查分析当前证明的前提与关系，不扩成全系统反例搜索；
- 后果分析引用已有取舍，新的可接受性通常向授权主体确认。

## 7. 成稿、压缩与确认

用户先要求完整成稿，再要求压缩，并要求说明哪些合并、删节、改写与新增示例能够保留作用。助手提出把重复定义合并、方法论收为四部分、Q&A 合并、测试的三个证明对象前移，以及增加判别性案例。

用户最后要求“不要落盘，直接输出 SKILL 文本”。助手输出压缩稿；用户随后表示已保存该稿，要求现在正式发布至 prompts 仓库的 current，并保存讨论记录与类似 occams-razor 的文档沿革。

## 8. 此次发布的范围

此次发布采用用户确认的压缩稿，不以历史草稿覆盖它。发布包括现役正文、脱敏讨论记录、发生记录、概念整理和经验反思。

原 review 的重新筛选另作为一次使用测试：交给 GLM-5.4 应用现役 SKILL，再由主代理核对。它的结果不能倒写为本次讨论中早已成立的结论。GitHub review 是否调整另依后续授权处理。
