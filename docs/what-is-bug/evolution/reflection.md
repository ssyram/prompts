# What is a Bug：经验反思

本文从本次会话提取经验。它是后见分析；事实顺序见[发生记录](archaeology.md)，用户纠正与助手原话见[讨论记录](../../../what-is-bug-discussion-log.md)。

## 1. 运行事实与 Bug 结论之间，仍有规范与合法性关系

本次助手曾以“新增测试在原实现通过、在修改后失败”作为意见有实证的标志。该操作可以证明测试能识别某项实现变化；原系统当前已有 Bug，还需要它在合法执行中违背规范意图的证明。

实践建议：先写清实验的证明对象，再给测试结果定名。边界：测试体系自身也可作为分析对象，但须有针对该体系的规范意图。

## 2. 模拟场景也承担可达性证明义务

暂停内部任务能观察时序，也可能顺带冻结真实的取消或超时条件。只证明模拟状态里有结果，尚需说明真实合法使用如何形成对应条件。

实践建议：对每个主动控制的条件说明其真实对应物，以及相关约束怎样保持。边界：这针对当前证明依赖的条件，不要求穷举全系统反例。

## 3. 局部检查与全面义务分开

作者给部分位置加检查，可以提供同类遗漏的排查线索；把其升级为“每个位置都必须有检查”，需要规范或推导根据。

实践建议：先表达为线索，再按当前论域分析其义务与后果。边界：宽泛设计讨论可以容纳抽象的一致性原则，严格交付审查需要相应入域根据。

## 4. 文档差异要证明共同适用与不相容

同词不同义、历史规范与当前规范、事实说明与行为要求，都可能呈现字面差异。规范冲突需要两端在当前情境共同适用且内容不相容。

实践建议：先写两端各自约束什么，再给最短冲突论证。边界：已明确取代的历史文本可以保留历史价值；未说明取代关系而造成执行者收到互斥要求，仍可作为候选分析。

## 5. 结构化表达不代替成立根据

本次多次重排“场景、意图、后果、证据”的格式，用户仍指出意图由助手发明、术语难懂或触发条件未闭合。表格完整不等于证明完整。

实践建议：检查每个结论依赖哪些前提及其根据，叙述只承载这条关系。边界：模板仍有帮助，但其作用是表达与分析，不是自动认证。

## 6. 原意、取舍与实际代价分别陈述

用户要求将常识期待、作者选择、作者所写代价、实际结果分别说明。把“作者选择串行”写成“系统理应串行”会悄悄给设计选择增加规范权威。

实践建议：清楚说明是谁作了何种要求或选择，以及哪些后果被明确纳入取舍。边界：作者表达的取舍也可能相互冲突，需以当前有效关系判断。

## 7. 历史记录不做胜出版本的辩护书

本次讨论包含项目专属草稿、绝对化排除规则、对用途的过度限制、随后逐项修订。保留这些消息，可以看见每项修订回应的实际问题。

实践建议：发生记录和后见分析分开，错误答复仍作为当时答复记录；它们的后续否定另作事件。边界：脱敏整理不是逐字会话的完全重放，删节规则须公开。
