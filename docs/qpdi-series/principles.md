# QPDI Series — 需求与原则

## Task Overview

QPDI Series 处理的是同一个委托中的两类问题：模型如何正确理解并组织 Q/P/D/I，以及如何把其中的 Q 与递归 D 写成稳定工件。当前 official 已运行，draft 正在做最小充分重组。

本文记录稳定需求；具体 P/M/R 见 [`architecture.md`](architecture.md)，变化来源见 [`evolution/README.md`](evolution/README.md)。

## 整体问题意识

AI 可以承担展开、推导、整理和实现，但人的规范方向不能在委托过程中被事实、经验、局部设计或实现便利替换。QPDI 的核心价值，是让 AI 保全这条边界，同时把复杂材料组织成能够继续设计、实现和检查的关系。

Q 不是人的总体思想画像，而是问题意识面向当前对象形成的有限结构：Q.I 定义判断方向，Q.A 承载被采纳的认知前提，Q.E 承载实际参与论证的经验依据。三者的边界来自当前问题中的功能，不来自外部人格分类。

`/qpdi` 提供认知与对齐；`/qpdi-compose` 把已识别内容写成 Q 与任意深度 D。二者可以独立调用，工作流和格式均可被用户覆盖。

## Q.I — 已确认需求

### Q.I.1 人保有规范方向

Q.I 中“什么正确、真正想要什么、边界在哪里”由人确认。事实、经验、失败、AI 推断和设计限制不能自行生成或降低这一方向。

### Q.I.2 模型能够直接使用

`/qpdi` 应让模型直接理解 Q、P、D、I、SCCO 和层间关系，并用于分析、回答、整理或执行；它不是只供人阅读的理论摘要，也不要求自动实现一套固定工作引擎。

### Q.I.3 复合话语不被标签化损坏

用户话语可能同时包含论域、前提、证据、推导、失败 pattern 和解决方案。系统必须先保全 proof，再按真实作用锚定，不能只做关键词到层级的映射。

### Q.I.4 Q 同时可引用且可整体理解

Q.I/Q.A/Q.E 条目必须能独立确认、挑战和引用；材料确有整体关系时，读者还应看懂它们为何共同出现、如何展开、限制或保持张力。整体组织不得复制 Q、强造单一中心或取得未经确认的规范权威。

### Q.I.5 Compose 产出可交接的 Q/D

`/qpdi-compose` 应能从原话和既有材料写 Q、D.root 与任意深度 D-frame，使后续读者能找到上游义务、P、M、R 和下一步去向。

### Q.I.6 D 深度由真实设计决定

D 不固定为 architecture/detail 两层。仍有独立语义、组合、分支、失败或跨工件义务时继续展开；已足以判断 I 是否正确承接时成为叶子，不制造空层。

### Q.I.7 最小充分而非最短

工作流、字段和可见格式都应可缩减、可覆盖。删除内容必须证明不会损害正确理解、完整设计、导航或交接；已有篇幅和结构也不能自行证明必要。

## Q.A — 当前成立的工作前提

- `/qpdi` 与 `/qpdi-compose` 是可单独调用的 prompt；Compose 因此必须自包含写作所需的最小 QPDI 核心。
- I 高度依赖项目和工件类型；Compose 只写到足以交接 I，不生成代码、配置、命令或具体实现步骤。
- SCCO 的系统性召回、攻击和裁决已有专项 prompt；`/qpdi` 仍需定义 SCCO，Compose 只保证 P/M/R 可检查。
- 项目可能有任意深度和既有文档结构；落盘应服从真实 ownership，而不是固定仓库根或固定目录树。
- 内容采纳、事实证据和文件写入授权是三个独立状态，不能相互推出。

## Q.E — 形成当前需求的经验

- 项目内外并存的 QPDI skill 会造成权威漂移，因此运行入口收敛为全局 `/qpdi`。
- 把静态知识、自动流程和文件 schema 混在一起，会让模型为遵守形式而偏离用户论域，因此静态认知与可覆盖工作流必须分开。
- 只列平面 Q 条目会保留局部精度，却丢失问题整体；反过来强造最高 idea 又会压平真实差异。
- component 分别满足 contract，不足以证明 composition 作为 whole 满足 P。
- 局部 D/I 暴露限制时，直接修改 Q 或把限制向下传播都会错置责任；必须逐层比较实际 guarantee 与 parent contract。
- 字段、状态、trace、反模式和 I 类型清单若没有独立消费者，会令 Compose 膨胀并掩盖核心写作任务。

这些经验只支持当前项目中的设计压力；它们不证明所有任务都必须显式展开完整 QPDI。

## 使用条件

| 情形 | `/qpdi` | `/qpdi-compose` |
|---|---|---|
| 复合论证、失败分析、跨层变化、规范偷换风险 | 使用；必要时显示论域/论证/锚定/行动 | 只有要形成稳定 Q/D 时使用 |
| 编写或重组 principles/design 文档 | 用于先识别内容关系 | 使用 |
| 简单事实问答或边界明确的局部操作 | 内部轻量应用；不展示脚手架 | 通常不用 |
| 直接编写 I | 可检查其上游 D | 不负责 |
| 系统性 SCCO 审查 | 提供概念基础 | 不代替专项审查 |

显式程度由结构风险决定，不由项目大小、文件数量或用户是否使用了某个术语决定。

## 成功标准

一次合格使用至少应做到：

1. Q.I、Q.A、Q.E 不互相冒充，candidate Q 没有被模型自行确认；
2. 用户 proof 的决定性前提、推导、边界和真实分歧仍然存在；
3. root 与 child 的规范来源不同，child 不绕过 parent contract 重解 Q.I；
4. P 的 owner/scope 清楚，M 同时包含 components 与 composition，R 能说明 Derivation、Satisfaction 和必要的 Optimality；
5. whole-level 义务、实际 guarantee 与未闭合项没有被局部 pass 隐藏；
6. component 明确继续展开或交给 I，I 的验证目标是具体化 M 并保持 P；
7. 输出完成 re-unification，没有把状态、角色、视角和表达形式伪造成新本体；
8. 用户指定的格式、范围和写入授权得到遵守。

## 非目标

- 固定阶段、角色数量、审查法庭或自动执行引擎；
- 强制所有回答展示 Q/P/D/I 模板；
- 固定 D 层数、文件名或仓库根目录；
- 由 AI 自行修订正式 Q、接受新风险或替用户作真实取舍；
- 在 Compose 内生成 I 或复制专项 SCCO 审查流程；
- 用故事、口号、完整清单或篇幅本身替代论证。

## Q → Design handoff

| 需求 | 主要设计承接 |
|---|---|
| Q.I.1–Q.I.3 | 内容角色、用户 proof 保全、Structural Locality 与 candidate 边界 |
| Q.I.4 | 条目化 Q + 非权威 whole view |
| Q.I.5–Q.I.6 | 递归 `D-frame = P + M + R`、叶子判据与 I handoff |
| Q.I.7 | re-unification、消费者门槛和可覆盖工作流 |
