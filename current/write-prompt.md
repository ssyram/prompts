# 写提示词

根据本轮材料，编写或修改提示词、角色说明或状态定义（含 YAML）。

本轮材料：
$ARGUMENTS

以下是写作方法，可按需要往返调整，不是固定流水线；不要自动把方法本身写进成稿。

## 1. 校准当前任务

先应用 `/recalibration`，回顾因何到此，明确本阶段要做什么、哪些约束必须满足、哪些只是可选建议，以及上游已给定的预算、假设、输入和上下文。沿用仍有效的材料，只补影响当前任务的缺口，不为局部写作重查整个项目。

## 2. 按需求写骨架

用一句话说明角色与任务，再写清目标效果、必要约束、实现方法或推荐工作流。让执行者凭已得到的上下文知道拿什么做、交什么、怎样算完；区分必须遵守的约束与可以调整的建议。

## 3. 补足必要条件

逐段、逐句检查结构和逻辑，补足执行所需的条件。优先用读者已懂的词；陌生词先看能否删除，必须保留的只解释到能据此行动。用 `/occams-razor` 检查每句话、每个前提是否确有任务需要，不为介绍背景复述整个系统。

## 4. 澄清的道与术

“道”是要达到的理解效果；“术”是该层可执行的动作。先选层，再选术，不把某个术误当成并列的道。威力按消除多少理解成本分级；前一层能解决就不进入后一层。

### 第一层：消解（优先，威力最大）

**道：让歧义概念不必再被解释。**

可用的术：删除无任务贡献的术语；合并同义词；同一个词只保留一个含义；把内部隐喻换成任务已有的说法；一词多义时先拆成不同名称。

判据：删掉或换名后，执行者仍能完成任务，就不应保留原概念。不能用“也许以后有用”保住它。

### 第二层：直陈与锚定（主干）

**道：用执行者已有的概念，给出可判定的定义、对象和条件。**

可用的术：

- **维度拆分**：把混合判断拆成正交维度，再分别直陈。例如“快”可拆成计算耗时、调用往返、等待时间；它是直陈的术，不是独立的道。
- **操作性定义**：把“X 是什么”改写成“怎样判定 X”。例如“无依据工作”定义为“删掉后没有任何已确认目标无法完成”。
- **指称锚定**：把词直接锚到实际文件、行号、运行、回执或工件；能指给读者看，就不另造解释。
- **条件直陈**：写全谁对什么、在什么范围、什么条件下做什么；避免“基本、合理、尽量、较短”等没有判据的词。
- **主干与例外分句**：先写主规则，再另写例外；不要在一句里堆多个限定从句。

直陈的边界：链条最终会碰到无法再用已知词定义的概念；这时用下一层实例落地，不靠造一个看似精密的新定义继续绕。

### 第三层：示例与辩护（直陈仍不足时）

这里有两种不同的道，不要混用：

**道 A：用语境传达无法明言的差别。**
可用的术：使用真实材料构造最小例子；需要区分两种读法时，构造只在关键维度不同的一对案例，让正例通过、反例失败。判别性反例属于这里，不属于模糊排除法。虚构例子只能解释规则，不能证明现实能力。

**道 B：说明为什么必须有这个规则或概念。**
可用的术：做删除测试（删掉它，哪个判断或执行步骤失败）；给出真实失效场景；说明这句澄清让读者新获得什么判断能力。辩护必须落到具体贡献，不能只宣称“更严谨、更完整”。

### 第四层：边界补充（迫不得已才用）

**道：在主定义已经成立后，消除剩余的特定误读。**

可用的术：在主规则之后补 corner case；若用反例，给出判定结果和适用范围。不要只罗列“不是 X、不是 Y、也不完全是 Z”来代替正确定义；排除清单无法证明已覆盖所有错误读法，也不能单独承担边界判断。

每句澄清最终都要回答：它让执行者能够判定什么此前不能判定的事？答不出，就不是必要澄清。

## 5. 减少并稳固前提

结合 `/recalibration` 与 `/occams-razor`，逐一检查依赖的前提：是否必需、能否解除，或能否换成更稳定的前提。不能为了简短削弱目标或必要约束。

前提越少，系统越稳；前提越稳，系统越稳。稳定的上游前提可以直接采用，无须重复解释。例如，状态只能经前态门禁到达，就直接假定门禁已通过，不再复述进入路径。

## 何时交付

执行者凭实际已得到的稳定上下文，能明确任务、输入、产物和结束条件，且每段都有必要作用，就停止。以提示词成稿为主交付，只补影响使用的未决项，无须另交回顾、逐句诊断或过程文档。

## 补充说明与常见误区（不增加步骤）

“最小充分”是执行所需信息足够、又没有多余内容，不是单纯追求字少。“前提”是任务可以依赖的条件，“约束”是必须遵守的要求。

- 字少不一定清楚：省掉必要解释，让执行者猜，反而不充分。
- 少前提不等于不用稳定前提：已得到的稳定上下文可以直接采用，不必让每个状态从零解释全系统。
- 常见不等于稳定：不要把“通常如此”或猜测冒充稳定的已知条件。
- 删去前提说明不等于解除实际依赖；如果需要改变上游职责，不能只改文案就算解除。
- 推荐方法不是硬步骤：可以往返调整，也不应把这套写作方法自动塞给最终执行者再走一遍。
