# 写提示词

根据本轮材料，编写或修改提示词、角色说明或状态定义（含 YAML）。

本轮材料：
$ARGUMENTS

以下是写作方法，可按需要往返调整，不是固定流水线；不要自动把方法本身写进成稿。

## 1. 校准当前任务

先应用 `/recalibration`，回顾因何到此，明确本阶段要做什么、哪些约束必须满足、哪些只是可选建议，以及上游已给定的预算、假设、输入和上下文。沿用仍有效的材料，只补影响当前任务的缺口，不为局部写作重查整个项目。

## 2. 按需求写骨架

用一句话说明角色与任务，再写清目标效果、必要约束、实现方法或推荐工作流。让执行者凭已得到的上下文知道拿什么做、交什么、怎样算完；区分必须遵守的约束与可以调整的建议。

## 3. 补足必要条件

逐段、逐句检查结构和逻辑，补足执行所需的条件。优先用读者已懂的词；陌生词先看能否删除，必须保留的只解释到能据此行动。用 `/occams-razor` 检查每句话、每个前提是否确有任务需要，不为介绍背景复述整个系统。

## 4. 减少并稳固前提

结合 `/recalibration` 与 `/occams-razor`，逐一检查依赖的前提：是否必需、能否解除，或能否换成更稳定的前提。不能为了简短削弱目标或必要约束。

前提越少，系统越稳；前提越稳，系统越稳。稳定的上游前提可以直接采用，无须重复解释。例如，状态只能经前态门禁到达，就直接假定门禁已通过，不再复述进入路径。

## 何时交付

执行者凭实际已得到的稳定上下文，能明确任务、输入、产物和结束条件，且每段都有必要作用，就停止。以提示词成稿为主交付，只补影响使用的未决项，无须另交回顾、逐句诊断或过程文档。

## 补充说明与常见误区（不增加步骤）

“最小充分”是执行所需信息足够、又没有多余内容，不是单纯追求字少。“前提”是任务可以依赖的条件，“约束”是必须遵守的要求。

- 字少不一定清楚：省掉必要解释，让执行者猜，反而不充分。
- 少前提不等于不用稳定前提：已得到的稳定上下文可以直接采用，不必让每个状态从零解释全系统。
- 常见不等于稳定：不要把“通常如此”或猜测冒充稳定的已知条件。
- 删去前提说明不等于解除实际依赖；如果需要改变上游职责，不能只改文案就算解除。
- 推荐方法不是硬步骤：可以往返调整，也不应把这套写作方法自动塞给最终执行者再走一遍。
