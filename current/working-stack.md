# Working stacks

任务材料：
$ARGUMENTS

## 是什么、为谁服务

Working-stack 是**用户拥有、AI 协助维护的当前工作状态**：哪项目标还成立，现在哪件事占据注意力，下一步做什么，何时能回到上一层。它是一棵带稳定 ID 的帧树；默认沿单路径推进，用户需要并行维护时，同一父帧可同时 push 多个子帧（parallel, para）。整个工作树只有一个选中的 `TOP`；其他分支保留为 `PAUSED`，逐一写明暂停原因。后台执行是否在途另记，不能据此增加第二个 `TOP`。它不是聊天流水账、完整项目设计、AI 的任务列表或完成证明。方法不能反过来替用户决定目标，更不授权启动实验、修改业务文件或扩大审查。

用户要能从栈顶回答：**我在做什么？为什么现在做它？做完回哪里？** 根帧保留整体目的，已 pop 帧保留完成事项与仍有效的学习。

## 何时建议建立或使用

- 当工作跨多轮、多阶段或多个独立方向，已有中断、返回、长期阻塞、上下文压缩，或者用户反复问“我们现在做到哪、下一步是什么”，建议建立工作栈；先说明它能恢复的具体焦点，请用户决定是否采用。简单的一问一答不必建栈。
- 当用户已持有工作栈，开始新工作前先找现有顶帧，而不是另起一份；出现真实的独立目的才另开工作线。用户直接规定帧结构、顺序或粒度时以其规定为准。

## 一个工作栈文件如何组织

用标题和一句话先交代工作线的名称／简称、整体任务和作用范围。随后按下列结构放内容；括号中的区块仅在有内容时出现：

```text
# 工作线名称（Stack A）
整体任务与边界

## 栈状态
[A-01] 根任务
[A-02] 中间在栈帧
...
[A-N] [TOP|PAUSED] 当前任务

（## 待归属缓存：暂未进入帧或其他工件的非平凡内容，按需分节）

## [A-01] [ACTIVE] 根帧
## [A-02] [ACTIVE] 中间在栈帧
## ...
## [A-N] [TOP|PAUSED] 当前帧
## [A-K] [POPPED] 已弹帧

（## 附录：用户确需时）
```

`## 栈状态` **只列仍在栈内的帧**，不列 popped 节点或虚拟栈底。没有活动帧就写“空”。

- 无 para 时维持原来的自然向下列表：从根到末尾，每帧一行 ID 和短名称，唯末行标 `[TOP]` 或 `[PAUSED]`。
- 有 para 时，只在分叉处用 `- ` 表示兄弟分支；其下的单路径缩进后自然向下写，不给每层都加树枝。下方例子给出具体形状。
- `TOP` 是唯一注意力焦点；未选中分支的末帧标 `PAUSED`，暂停原因写在该帧正文。整线暂停时可以没有 `TOP`。
- 上帧字段仍是父子关系的记录；para 是一个父帧拥有多个子边，每个子帧仍只有一个上帧，不引入多父节点。

帧正文按概览顺序先写全部在栈帧，再写全部 popped 帧；切换分支只更新选择状态、FOCUS 和暂停原因，不改 ID／上帧，也不冒充 pop。新 push 插在 popped 区之前；pop 后保留原 ID 与历史，移入 popped 区。`[digression]` 仍在概览标明，如 `[TOP/digression]`。待归属缓存不作为已确立原则，能够归属时移入对应帧。

## 一帧包含什么

每帧 ID 稳定、不重用。root 和 `[digression]` 的**来源**须说明为何存在；普通子帧简述使上帧暂时挂起的问题。

实际帧标题标 `[ACTIVE|TOP|PAUSED|POPPED]`。`ACTIVE` 表示仍承担责任的父帧，不是第二个焦点；每个 `PAUSED` 帧在正文写 `暂停原因`。`POPPED` 只表示回合已退出，达成情况另写 `done` 或 `expire` 及依据，不能把暂停直接写成完成。

帧内按此顺序写，简单项用列表，复杂项才在**原位置**升为 `###`，不为统一格式拆成更多文件：

| 栏目 | 要回答的问题 |
|---|---|
| 上帧、来源、弹帧目标 | 从哪项责任而来？何以成立？什么条件允许 pop？ |
| 达成情况（仅 popped，紧接目标） | **结果**是什么？它**如何对应**原弹帧目标？完成记 `done`；未完成而退出记 `expire` 并说明理由。 |
| 计划 | 属于本帧的 `done`／`in_progress`／`ready`／`blocked` / `[expire: EXPLAIN]` (e.g., `[expire: 部分，详见 A-02 的完成情况节]`) 项；活动帧须有一个可指出的 **FOCUS**。父帧自己陈述任务，不用子帧 ID 代写。 |
| 已得结果 | **本帧目标获得了什么非平凡的对应弹帧目标的收获**？一项一行。学习型目标下，有依据、获用户认可的新理解也可交付，但是只能对应弹帧目标，非对应者考虑添加到备注中；`[认知习得]`／`[实验结果]` 等标签可选，不是固定枚举。 |
| 外部执行事项 | 本帧造成了什么可观察的外部副作用，如写文件、提交、停或启进程？只读调研与“未改文件”不是副作用；无则写“无”。 |
| 确立原则 | 用户明确确认、后续须遵循的局部规则或临时设计决策是什么？事实再重要、AI 写成命令句，也不会自动获得规范效力。 |
| 备注 · <名称>／备注 | 还需保留却不属于上述栏目的事实、用户新增认知、待核判断或背景；可以多条，可自命名，注明证据状态。 |


## 如何记录与推进

1. **恢复目的。** 读用户最初要求、明确纠正和已接受裁决，再看当前栈；把想要、已执行、已验证、已接受及待核判断分开。运行代号或最近产物不能顶替根目标；被新裁决覆盖的旧目标只留作历史。
2. **筛内容、找位置。** 先问内容是否非平凡：是否直接占据用户任务，形成值得保留的认知，交付结果，或改变下一步？再从根到局部找最贴近其目的的帧。不能因为一项很重要，就在每层祖先重复记账。
3. **判栏目。** 按上表将目标收获、用户确立的约束和其他有价值内容分别归入结果、原则与备注；**另判**有无实际外部副作用。未获确认的推导只作待核备注。
4. **维护计划和活路。** 非微小计划项按下一步默认 push；微小推进可只改本帧计划状态与 FOCUS。活动顶帧始终指出一个当前工作项；若不能行动，就写明谁的哪项决定或哪份证据在阻断，并继续不依赖它的现有工作。计划全做完而弹帧目标未达时，短暂 push planning 帧找有依据的下一项，返回后扩充原帧。不可用笼统“等待”、虚构 done 或无目的的反复审核维持表面活跃。
5. **Push / Push parallel / 切换。** 开始非微小的计划项时，给它子帧、来源、FOCUS 与细化父目标的弹帧目标；用户修订后不随意改目标。需要并行维护时，同一父帧可同时保留多个未结束子帧，每个子帧仍只有一个上帧。只选一个末帧为 `TOP`，其他分支末帧标 `PAUSED` 并写原因；被选路径的父帧仍是 `ACTIVE`。切换时将旧顶设为 `PAUSED`、说明原因，再将所选分支末帧设为 `TOP`，保留各自计划、结果和 ID。后台任务的运行／阻塞状态单独记在所属帧，`PAUSED` 不自动停止任务。单个子帧完成不代表兄弟分支或父项完成。微小推进留本帧，不为工具调用空造帧；独立旁支可用 `[digression]`。
6. **Pop。** 回顾本帧整棵执行子树，对照**原弹帧目标**，在已有“达成情况”中先用“结果”概括整体关系，再于“对应／依据”逐点写正向（原目标自身实现了什么）、反向（目标本体或其认知前提被怎样推翻）、正交（原目标外但有来源依据证明符合原意并丰富目标的收获）；逐点给证据，来源关系不明不冒称正交。方向可并存，只写实际发生者，不新增栏目。目标已达则核实后记 `done`。用户确认终止、替换或不再继续这个执行回合时记 `expire` 并写明理由，不记完成；若整体目标仍需继续、旧回合只交付部分，写 `[expire: partial, see ID]` 指向承接帧或任务，原结果和未完成义务都保留。仅暂时挂起而未退出的分支仍是 `PAUSED`，写暂停原因，不 expire。反例可完成“判真假”，却不能假装完成“证真”；目标仍重要且没有终止／承接裁决时，更新计划，不假 pop。逐父帧说明子结果能否支撑父目标，不追改旧目标或以子帧成功冒充父项完成。已 pop 帧不得重回活动路径；可补历史说明，新的独立目标另建帧并在来源中引用旧 ID。保留原帧的 ID、计划、结果、备注和原则。
   - 只把执行子树中仍与上层目标有关的关键结果、原则和外部副作用概括到父帧，或留节点指针；失效内容只留历史，不向所有祖先重复抄录。活动帧在 pop 前不预写下层汇总。
   - 原则逐条标 `released → <接收处 ID>` 或 `kept-local`；过期帧的原则不自动上移。被推翻的标 `invalidated` 和理由；误列为原则的保留原 ID、移至合适结果或备注并标 `reclassified`。若旧项曾 `released`，还须说明原去向并同步接收处；改类不等于判原事实为假。
   - 弹帧后**向用户说清返回上帧的状态、残余分支与下一项**；para 下若转向兄弟分支，明确唯一 `TOP` 的选择及其他分支暂停原因。Native task 的关闭同样只有 done／expired：有可核达成才 done，partial 退出用 expire 并在 reason 中链接承接任务；paused 活任务不强行关闭。

## 与用户协作、收尾及持久化

- 用户是工作栈的 owner。AI 可指出焦点漂移、缺失的返回条件、已具备 pop 证据或值得单列的旁支，并给出倾向；不能因用户继续对话、沉默或 AI 的自述就认定用户批准新原则或验收整个任务。提建议不等于擅自 push/pop。
- 建议 pop 时说清：“本帧目标是 X；已获得 Y，尚缺 Z；因此建议 pop／暂不 pop，返回后做 W。你确认吗？”发现可能岔题时说清：“当前主线 X 仍未完成；新问题 Y 是否需要暂以 `[digression]` 处理，之后返回 X？”不替用户回答这两个问题。
- **结束一个工作段或准备停止前**，快速看当前顶、根目标、弹帧目标和下一项是否仍相连：本轮是否有非平凡结果要记、是否有已执行的副作用、是否只剩没有出口的等待？必要时更新相应帧并告诉用户当前顶与下一步；没变化就不更新、不为每句提交。简短不能靠省略 FOCUS、已完成项或确立原则的可见性获得；这也不是追加审查轮次。
- 工具检索前说明所找事实和所需源锚；一般使用有定位的 impression，逐字／空白敏感时才读小段原文。不把后来的成功倒灌给先前帧，也不把同源报告的相互赞同当独立证实。
- 显式文件可按工作线分开：帧文件和全局原则记录保留目的、进度、用户裁决及来源；操作方法不能覆盖用户原始记录；新反馈若与之冲突，先按用户裁决修正相应帧，再同步方法。用户若指定 A/B 分文件、目录及独立无 remote 的本地 Git，就按该工作线的具体约定执行，不把这个目录推广为所有工作线的默认值。短回答先在会话中累积，有调研／工具任务时合并更新、只提交本轮确实改动的栈文件或方法文件并短报。
- 若具体工作线**已附**结构检查脚本，修改栈文件后、提交前按实际路径运行；本次本地工作栈的 `check_working_stacks.py` 与方法文件同在 `skill/`；其他工作线以其实际部署路径为准。它只核单路径／para 父链、唯一 TOP、暂停原因、pop 栏位和不复活的结构，不代替用户判断目标是否达成；其他工作线没附脚本不因此阻塞，纯答复不为它另调工具。
- 短讨论可以暂时执行，并简单在对话 transcript 中记录将要对 Stack 作的更新，等后续用户确认或者做其他更大的操作的时候再正式连续更新栈文件。

## 例子

**同一父帧并行维护两个分支。**只有分叉处画树枝，其余路径自然向下：

```text
[W-01] 根任务
- [W-02] 设计审阅
  [W-04] [TOP] 审阅当前接口
- [W-03] [PAUSED] 实现审阅
```

W-02、W-03 的上帧都是 W-01；W-04 的上帧是 W-02。W-03 正文写“暂停原因：当前先审接口，保留实现审阅位置，用户切换时继续”。切到实现分支时，W-04 改为 PAUSED 并写原因，W-03 改为 TOP；不关闭 W-04，不重新 push 原 ID。

**旧回合只有部分成果。**用户终止旧执行回合并交新帧承接时，在旧帧达成情况写 `[expire: partial, see W-05]`，紧接退出理由、已得结果、未完成义务；新帧来源引用旧 ID。不要把整体目标写成 done，也不要把仍可原地继续的 PAUSED 分支一律 expire。

**学习目标也能交付结果。**若用户要理解某输入如何影响程序：

```markdown
## [W-02] [TOP] 理解输入边界
- 上帧：[W-01]。
- 来源：用户追问输入与处理对象的关系。
- 弹帧目标：用户学到配置选择与工具执行各自保证什么。

- 计划：
  - **[FOCUS/in_progress]** 对照实际配置和执行记录。

- 已得结果：
  - [认知习得] 工具按给定配置执行成功，不独立证明该配置符合用户原本的构建。

- 外部执行事项：无。

- 确立原则：无。
- 备注 · 待核：另一种输入路径尚未查清，不能说所有路径都如此。
```

**旁支完成后回到原目标。**用户正在比较运行成本 `[W-01]`，转而要求弄清一个独立的文档问题，可临时 push `[W-03] [digression]`；其来源须说明与成本问题的关系，但成本帧不因此算完成。若 `[W-03]` 里真的写了文件，外部执行事项只记该文件；若只读并得到答案，则可有结果而副作用仍为“无”。用户确认该问题解决后，将 `[W-03]` 标 `[POPPED]`，留下结果及目标下的达成情况，并在回复中说明回程：“返回 `[W-01]`，FOCUS 是比较同终点的耗时；下一项核对两个运行的终点是否一致。”

**计划完了不等于能 pop。**若 `[W-01]` 的计划项均已完成，但“完成可信比较”的弹帧目标仍缺可比终点，标明缺口；可短暂 push planning 帧，FOCUS 仅为找出获取终点的有据下一项，返回后补入 `[W-01]`。不以“全打勾”宣告比较完成。若用户改选别的目标、原比较已无继续价值，则在达成情况中写结果 `[expired]`、原目标为何不再重要及用户裁决；保留历史，不把比较记作完成。
