# Recalibration

本轮材料：
$ARGUMENTS

## 任务与交付模式

用 `/working-stack` 的帧结构理清目标树，先在内部逆向追清当前工作的来路，再从用户的授意出发，用**最短时间、最短路径**让用户知道现在的真实状况与下一步。它只负责复盘与对齐，不自动扩成方案重设计、砍步骤优化或额外审查，也不增减任何执行权限。

按场景选一种交付，默认不写文件（仅在用户明确要求或授权维护时落盘）：

- **对用户汇报（默认）**：逆向复盘在内部完成，对外只输出下方“模板一”。多条并行工作线就并排写多套，当前主线放最前。
- **显式复盘（用户要求看复盘过程，或执行者做阶段自检）**：输出“模板二”，把逆向因果图与校准结论写出来。

## 三步做法

### 1. 理清目标树

以用户的原话、后续纠正和已有栈为依据，整理出目标树。帧结构与状态（`TOP`、`PAUSED`、`DONE`、`EXPIRED` 及父子/并行关系）直接沿用 `/working-stack`，不另造第二套状态名。

树干只记录用户的目标、范围裁决、暂停/取消决定和验收条件，全部用用户已有的概念表达，不放执行方自造的过程词、脚本名或批次号。必须先立住这棵树，后面才能判断：哪些内容是用户本来就知道并关心的，哪些只是执行方自己的中间过程。

没有现成栈时，按当前上下文当场构建；已有栈时继承并修改对应节点。用户的纠正要改到受影响的原帧和父计划上，不要只往末尾追加新项，否则旧方向仍会留在树里干扰判断。

### 2. 逆向追原因

从手头正在做的一件或多件事出发，逐步往回问“现在做 B 是因为之前发生了什么”，一路追回两类起点：

- **授意起点**：用户哪句话要求做、允许做或改了方向；
- **事实起点**：途中实际核实到的客观限制、外部阻塞，或改变目标可行性的证据。

这一步还原的是**真实历史因果图**，允许并行推进、一件事有多个原因、多条支路汇合到现在：

- 只连真实因果，不把时间上碰巧先后发生写成因果；
- 事实起点和中间结论以源码、运行结果和原始记录为准，不拿猜测补链；
- 不要求证明每一步“非这样做不可”——这里只如实还原怎么走到现在的；
- 若某项工作追不回任何用户授意或实际事实需要，标为**未挂接工作**，不硬凑理由塞回目标树。

### 3. 顺向最短路径讲解

顺向讲解的唯一目标是：**用最短路径让用户掌握现在的状况；凡是用户不知道、也无需知道就能理解现状和做决定的内容，一概不说。**

把逆向追清的图翻过来，从各个用户授意节点直接连向当前状态，按五条规则裁剪（配正反对照）：

- **按“用户理解 B 是否必须先知道 A”决定去留，不按历史先后讲过程**：历史上“先试了 A 走不通、所以改做 B”，只要用户不靠 A 也能直接理解现在的方案 B 及其效果，A 就直接不提，直接讲 B。只有当 B 的存在本身离开 A 发现的客观限制就无法解释（例如原定目标因该限制无法按原要求达成、需要改目标或边界），才用一句话交代那个限制；用户可能会顺手追问“为什么没用 A”时，至多放进第三节末尾的可选补充问答里一笔带过，不放进主干叙述。底层记录保留备查。
  - 反例：“我先试了方案甲走不通，所以改走方案乙，现在乙做到……”（乙本身直接可懂，硬把历史弯路甲塞进主路径，浪费用户时间）
  - 正例：“按你要的目标，现采用方案乙，目前已做到……”（直接走最短路径；若甲真是用户可能好奇的备选，只在末尾可选问答补一句不用甲的原因）
- **已做完的直接摆结果与证据，不讲中间过程**：某件事已经做完，直接给结论、覆盖范围和验证依据，不回放中间改了几轮、踩过什么坑。
- **新概念先接回用户要求**：内部指标、阶段名或检查项只有在第三节确有必要时才引入，且先交代它核对用户的哪条要求、起什么作用。
  - 反例：“四个等待窗口零重叠，原因是……”（内部词裸上场，用户不知道为什么突然看这个）
  - 正例：“你要求每轮单独核对‘并行是否真发生’；这一项本次未触发，核对调度规则确认是当前测试输入本身没有可并行的两批任务。”（先接回用户要求，再给核实后的定案）
- **旧认知需要更正时，直接给现定案与依据**：只有当某个旧说法已经进入用户认知、现在被新证据推翻时，才从该共同起点直接说明“现核实结果是什么、依据是什么”，不展开查错过程；用户从未听过的中间误判一律不提。
- **做完与验收分开**：帧达到约定条件但尚待用户确认时，不改标 `DONE`，而是在当前进展里直接摆出完成依据请用户验收；用户未表态只记待确认，不把沉默当通过。若某分支已具备完成依据、按既有授权转去恢复另一条 `PAUSED` 分支，直接写清：本支的完成依据、满足了哪条恢复条件、现已转回哪一帧继续。

## 模板一：对用户汇报（默认，每条并行工作线一套）

```markdown
## 工作线：<工作线名称>

### 一、目标树干
<一句话写清本线总目标>
- [W-01] <根目标与验收条件> —— 来源：<用户最初授意>
  - [W-02] [DONE] <已验收子目标> —— 来源：<用户哪句话>；结果：<一句定案>
  - [W-03] [EXPIRED] <已取消/改向子目标> —— 来源：<用户改向的话>；保留成果：<无则省略>
  - [W-04] [PAUSED] <暂停子目标> —— 来源：<用户哪句话>；暂停原因与恢复条件：<等什么>
  - [W-05] [TOP] <当前主攻子目标> —— 来源：<用户哪句话>；当前责任：<正在完成什么>

### 二、需求沿革
<用一段连贯的话把第一节讲成时间线：最初要解决什么 → 用户在哪几处追问、
收紧标准或改了方向 → 因此现在停在什么目标结构上。
只写用户意图和裁决的演进，不写执行方的操作流水。>

### 三、当前进展
<从用户的授意节点走最短路径直达现状，不讲用户无需知道的过程：
- 已做完的项：直接摆结果、覆盖范围与完成依据（待用户确认的不自封 DONE）；
- 正在做的项：直接说当前方案与做到哪一步；只有离开某项客观限制就无法解释当前方案或边界变化时，才补一句该限制；
- 已完成本支并转回某条 PAUSED 分支的：写明本支完成依据与现已恢复的目标帧；
- 存在追不回任何授意或事实需要的未挂接工作时：单独列出并说明处理建议。>

<可选 · 补充问答（仅当存在用户很可能会问“为什么没走某常见备选”时才保留，否则整块删掉）：
- 为什么不用 <备选 A>：<一句核实过的原因>>

### 四、下一步
<先用一句接回这个目标为什么存在（对应用户哪条要求），再写现在已经具备什么条件，
因此下一步具体做什么、由谁做或等谁确认。>

**最终一句：<总目标> — <当前所处位置> — <下一步动作或待确认点>。**
```

## 模板二：显式复盘（仅在要求写出复盘过程或内部自检时使用）

```markdown
## 逆向复盘：<工作线名称>

### 一、目标树快照
<同模板一第一节，先固定回溯要对齐的用户目标树>

### 二、逆向因果图
- 当前动作 B：<正在做什么 / 已完成什么>
  <- 直接原因：<核实过的事件/发现/阻塞，附源码、运行或记录依据>
  <- 上游原因：<继续往回追，多因并列时分条写出>
  <- 起点：<接回 [W-xx] 用户授意，或接回某项独立事实起点>
- 未挂接工作：<追不回任何授意或事实起点的动作；无则写“无”>
- 对现状无决定作用的历史尝试：<仅内部留档备查，对外汇报时剔除；无则写“无”>

### 三、校准结论与下一步
- 目标树是否需修订：<例如发现原子目标受客观限制无法按原方式达成，需请用户裁决>
- 对外最短路径定案：<去掉过程与无关尝试后，用户真正需要知道的现状>
- 下一步：<具体动作或待裁决问题>
```

## 交付前核对

1. 一、二节是否完全站在用户目标与裁决上，零内部过程词？
2. 第三节是否做到了最短路径：凡是用户无需知道就能理解现状和做决定的历史尝试、中间过程，是否已经全部拿掉？
3. 已做完的事项是否直接摆出了结果与完成依据，而没有把“跑通/没报错/用户沉默”直接写成 `DONE`？
4. 确需引入的新概念是否只出现在第三节，且先交代了对应哪条用户要求？
5. 下一步是否说清了“为何做、已有什么、接下来谁做什么”？
